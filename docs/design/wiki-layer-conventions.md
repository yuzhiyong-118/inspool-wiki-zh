# Wiki 知识层约定：页面规范、图谱关系与入口分工

> 本文把私人知识层中仍然通用的规则提取为可发布设计。原始页面位于使用者的私有 `wiki/meta/` 目录，未随本仓库发布；这里保留的是规则本身，不含个人页面、真实链接与历史记录。
>
> 文中状态与约定对应原文写作时点（2026-04 至 2026-10），不代表当前部署或验收完成。门禁与角色权限的完整设计见 [维护方案](maintenance-plan.md)，运行时实现见 [运行时说明](../../tools/wiki_runtime/README.md)。

## 一、节点角色与关系原则

知识库分三层，`raw/` 是原始资料节点，`wiki/` 是结构化知识节点，`wiki/meta/` 是规则与元信息层：

| 层 | 角色 | 是否作为图谱主边 |
| --- | --- | --- |
| `raw/` | 原始资料节点，保留外部 URL 与原文 | 否 |
| `wiki/sources/` | 证据节点，来源摘要页 | 是 |
| `wiki/entities/` | 实体节点 | 是 |
| `wiki/concepts/` | 概念节点 | 是 |
| `wiki/synthesis/` | 综合判断节点 | 是 |

核心原则：**不把外部 URL 当作图谱中的主要关系边**。外部 URL 适合作为出处记录，不适合作为知识关系的主边；主边应连接本地 Markdown 节点。

这样做的收益是可点击的本地证据节点、更稳定的图谱结构，以及更好的页面聚合能力。代价是需要为每份来源维护一层摘要页。

## 二、页面规范

### 2.1 通用要求

- 默认全部使用中文，除非用户明确要求其他语言；
- 标题清楚，段落简洁；
- 尽量使用双向链接；
- 重要结论尽量附带来源页；
- 不确定内容必须标记出来；
- 关键证据优先链接到本地来源页，而不是直接贴外部 URL。

### 2.2 图谱友好写法

为同时服务阅读、Graph 展示与可查询关系，建议并行维护两类关系表达：

1. 正文里的显式双链——用于阅读与 Graph 展示；
2. frontmatter 里的结构化关系字段——用于查询与后续自动化。

只维护其一都会丢失另一类用途：只有正文双链则无法做结构化查询，只有 frontmatter 则人工核查成本高。

### 2.3 用户手动分类目录的兼容

使用者可以在 `concepts/`、`entities/`、`synthesis/` 下自建子文件夹做分类。这类子文件夹是**组织层，不是知识关系本身**。因此：

- 页面关系依然主要靠双链与 frontmatter 关系字段维护；
- 不要在正文里把某个子文件夹路径写成知识事实；
- 查询尽量针对顶层类型目录，不依赖某个固定子文件夹；
- 页面迁移后若需分类展示，优先更新索引页，不重写大量正文路径。

代理必须默认兼容这些子文件夹，不能把它们当作稳定不变的语义真相。

### 2.4 推荐 frontmatter

来源页：

```yaml
---
type: source
status: active
topic: ai-agents
updated: 2026-04-11
raw_note: "[[<知识库根目录>/raw/unprocessed/某篇原文]]"
external_url: https://example.com/article
related_entities:
  - "[[entities/某个实体]]"
related_concepts:
  - "[[concepts/LLM Wiki]]"
related_sources: []
---
```

实体页／概念页／综合页：

```yaml
---
type: concept
status: active
topic: ai-agents
updated: 2026-04-11
supports:
  - "[[sources/某篇来源]]"
contradicts: []
related_entities:
  - "[[entities/某个实体]]"
related_concepts:
  - "[[concepts/Agent Workflow]]"
related_sources:
  - "[[sources/另一篇来源]]"
related_synthesis: []
---
```

`supports` 与 `contradicts` 是最重要的两个字段，优先维护。

`raw_note` 使用库内可解析的 wiki 链接，优先写完整路径，并始终保持为 raw 文件的当前真实位置：

- ingest 阶段通常先指向 `raw/unprocessed/`；
- approve 迁移后必须同步改为 `raw/processed/`；
- 如果正文里写了“原始资料”链接，也必须与 `raw_note` 一起更新。

### 2.6 领域特定模板

ingest 时先判断来源类型，再选用对应模板；通用必填 section 始终保留。

| 来源类型 | 额外关注点 |
| --- | --- |
| 论文／技术文章 | 方法论；实验或基准结果；局限性（作者自述与自身判断） |
| 博客／观点文章 | 作者立场；论据质量（强／中／弱／待验证） |
| 聊天记录／讨论 | 讨论参与方；达成的共识；遗留分歧 |
| 会议纪要 | 会议目标；关键讨论；做出的决定；行动项（负责人与截止日期） |
| 日记／个人反思 | 事件摘要；关键洞察；情绪与状态；后续行动 |

引入日记类模板需要同步调整知识库的“不在范围”声明——原范围声明写明个人日记与情绪记录不进入本库，把个人随笔纳入范围属于范围变更，不是模板层面的自由选择。

### 2.7 引用规则

- 关键结论优先链接到本地来源页，例如 `[[sources/某篇来源]]`；
- 能定位到具体小节时优先使用锚点，例如 `[[sources/某篇来源#关键观点]]`；
- 外部 URL 尽量只保留在来源页的“来源信息”中；
- 证据不足时不要伪造 `supports`；
- 如果页面分类目录被调整，优先依赖可自动更新的链接，不要人工写死旧路径。

## 三、关系字段与落链方式

### 3.1 关系类型

| 类别 | 字段 | 含义 |
| --- | --- | --- |
| 证据边 | `supports` | 支持当前页面关键结论的来源 |
| 证据边 | `contradicts` | 与当前页面关键结论冲突的来源 |
| 主题边 | `related_entities` / `related_concepts` / `related_sources` / `related_synthesis` | 同主题的横向关系 |

这些关系字段推荐写在 frontmatter 中，同时在正文中用双链显式体现。

### 3.2 落链层级

- **页级证据链接**：适合 frontmatter 的 `supports` 列表，便于结构化查询；
- **段落级证据链接**：适合正文，便于人工核查。

两者用途不同，不是二选一。

### 3.3 建页职责

| 页面类型 | 主要职责 |
| --- | --- |
| 来源页 | 总结单个来源；回链 raw 原文；抽取实体、概念和相关来源；作为其他知识页的证据节点 |
| 实体页／概念页 | 形成主题骨架；维护 `supports` 与 `contradicts`；与相邻概念和实体建立关系 |
| 综合页 | 沉淀跨来源结论；显式展示支持证据与冲突证据；挂接相关实体、概念和来源 |

### 3.4 最小可用规则

如果不想一开始维护太多字段，至少保证：

1. 所有综合页都有 `supports`；
2. 所有关键概念页都有至少一个来源页链接；
3. 关键结论在正文里能落到 `[[sources/...#某节]]`。

## 四、工作流与状态机

### 4.1 总流程

1. 把原始资料放入 `raw/unprocessed/`；
2. 如有需要，用子文件夹或 `ingest_group` 组织成一个 ingest 单元；
3. 执行 ingest，把 raw 编译进 wiki，但不直接归档；
4. 审阅本次沉淀结果；
5. 审阅通过后执行 approve，把 raw 迁移到 `raw/processed/`，并回补 wiki 中的 raw 引用；
6. 日常问答优先基于 wiki，而不是直接回到 raw 做一次性总结；
7. 将高价值回答回填到 wiki；
8. 定期执行 lint，检查结构、证据链、状态机和图谱关系。

### 4.2 状态机

```
unprocessed  ──ingest──▶  pending_review  ──approve──▶  processed
```

- ingest 只会把 raw 推进到 `pending_review`；
- approve 才会把 raw 推进到 `processed`；
- 未经用户确认，不允许直接从 `unprocessed` 进入 `processed`。

### 4.3 ingest 单元

默认处理单位不是固定的“一篇”，而是一个 **ingest 单元**：一篇独立素材，或一组明确相关的素材。

判定优先级：

1. `raw/unprocessed/` 下同一子文件夹；
2. 相同 `ingest_group`；
3. 用户明确说明这几篇需要一起处理；
4. 否则按单篇处理。

建议单批次控制在 2 到 5 篇。

### 4.4 五类核心操作

| 操作 | 语义 |
| --- | --- |
| `ingest_raw` | 选择下一个 ingest 单元，创建或更新来源页／实体页／概念页／综合页，更新索引与日志，将 raw 标为 `pending_review` |
| `approve_ingest` | 找到最近一组 `pending_review` 的 raw，核对 wiki 页面存在后迁移到 `raw/processed/`，同步回补 raw 路径引用，更新索引与日志 |
| `query_wiki` | 优先读取内容索引，基于现有页面综合回答，关键判断优先引用本地来源页 |
| `inspool` | 把一次值得保留的问答沉淀回 wiki（默认优先综合页），同步更新索引与日志 |
| `lint_wiki` | 检查孤立页面、弱证据、重复页、旧路径残留、关系字段缺失、`pending_review` 积压，以及图谱中的 `supports`／`contradicts`／`related_*` |

### 4.5 默认语言

除非明确要求其他语言：知识沉淀文档、索引、日志、说明页和命令模板默认中文；raw 原始资料可保留原语言。

## 五、入口职责分层

规则正本、意图说明与状态快照三者容易互相覆盖，因此按“谁先说”分配权威：

| 层次 | 回答的问题 | 内容性质 |
| --- | --- | --- |
| 规则正本（`AGENTS.md`） | “Agent 应当如何做” | 规则：结构约定、状态机、关系字段语义、引用规则、禁止事项 |
| 意图说明 | “这个知识库是为了什么” | 意图：主题边界、正在追问的问题、范围说明 |
| 状态快照 | “现在做到哪了” | 状态：当前阶段、起步方式、当前待办 |

重叠时按此顺序取权威：规则正本对 Agent 行为规范优先，意图说明对目的优先，状态快照对当前进度优先。新内容按它回答的问题归属，不按出现的文件归属。

**与 ADR 的关系**：ADR 是设计决策的留痕，比上述三层更具确定性；上层可以引用 ADR，但 ADR 不依赖上层。一旦某条 ADR 改变了职责边界，需要同步调整对应入口的声明。

## 六、历史设计决策（ADR 摘要）

以下三条决策在原始工作区以 ADR 形式留痕，原文件位于私人知识层，未随本仓库发布；此处保留决策、备选与依据。

### ADR-0001：raw 流程状态由 frontmatter 承担，索引仅作查询快照

**状态**：提议（2026-07-16），采纳自多 Agent 审计报告 Day 1 推荐项。

**上下文**：raw 允许写入流程字段，同时存在一份维护队列与已处理记录的索引文件。审计中两条建议竞争：一是 raw 严格不可变、状态由外部索引承担；二是状态写在 raw frontmatter、索引只作查询视图。进一步的问题是：过期结论检测、查询排序、批准时的回补路径都依赖一个**真相源**。

| 选项 | 真相源 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. raw frontmatter | 每篇 raw 文件 | 不依赖外部索引；可随文件移动；git diff 即可审计 | 需要 frontmatter 必填；wiki 端反向同步校验 |
| B. 索引文件 | 唯一索引文件 | raw 严格不可变；单一真相 | 索引与 raw 路径双写风险；移动 raw 需同步 |
| C. 双写 | 两处 | 高可用 | 维护成本翻倍；不一致窗口期 |

**决定**：采纳 A——raw frontmatter 是流程状态的真相源，索引仅作查询快照与审计视图。

**依据**：纯 Markdown + Git 的用户驱动模式没有守护进程来保证严格不可变；git diff 与提交信息已构成审计链；检查与审核都依赖 frontmatter 字段，双写没有并发写入需求支撑。

**配套约束**：raw frontmatter 必填 `processing_status`（`unprocessed` / `pending_review` / `processed`）、`reviewed_at`、`processed_at`、`processed_into`；索引自动从 frontmatter 聚合生成，不手工维护；修改 frontmatter 默认允许，正文改写仍禁止。

**后果**：状态真相随文件走，迁移 raw 不丢状态；代价是必须靠 lint 兜底维持字段统一，若未来引入自动化守护进程需要重新评估。

**修改约束**：进入“已采纳”状态后，对应约束需同步进规则正本与相关命令模板；修改该决定必须以新 ADR 引用本 ADR 的方式出现，不能直接覆盖。

### ADR-0002：中文 raw 强制英文 title 可选；查询要求双语术语

**状态**：提议（2026-07-16），采纳自多 Agent 审计报告的待决项推荐值。

**上下文**：默认语言为中文，但素材来源混杂（中英双语剪藏、英文字幕、英文官方文档）；查询流程未做语言路由，可能漏掉纯英文标题的页面，反之亦然。

| 选项 | 描述 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 强制英文 title，查询双语并发 | 素材同时提供英文标题，查询先按中文检索再按英文术语反查 | 单一资料；召回率最大 | raw frontmatter 多填 1–2 个字段 |
| B. 维持现状 | 中英混杂，自由文本查询 | 零成本 | 召回漏；与“中文知识库”语义不一致 |
| C. 命名空间分离 | 新建独立英文库 | 严格 i18n | 维护成本翻倍；路径稳定性规则被牵动 |

**决定**：采纳 A。raw frontmatter 必须包含 `title`（原语言标题），`title_en` 与 `aliases_en` 可选但强烈建议在中文素材中补齐。查询第一步要求双语并发：先按中文关键词检索，再按 `title_en` 与 `aliases_en` 反查，最后回退到正文文本。

**依据**：检索召回率优先于存储统一——中文查询漏掉英文页面的代价更大；加字段是零行为变更、风险低；命名空间分离与路径稳定性规则直接冲突。

**后果**：中文查询不再漏英文页面；代价是已有素材需补英文标题，可由后续 ingest 流程自动补。

### ADR-0003：引入外部 Agent 作为常驻自动化维护者

**状态**：提议（2026-08-11），来自自动化接入方案的评审结论，与 ADR-0001、ADR-0002 一并生效。

**上下文**：五个核心操作此前只能由人或外部代理手动触发，没有自动化层的常驻守护。目标是在本机让一个常驻 Agent 自动运行这些操作，同时**严格遵守既有规则，不引入新的语义层**。

| 选项 | 自动化主体 | 触发入口 | 优点 | 代价 |
| --- | --- | --- | --- | --- |
| A. 常驻 Agent 守护进程 | Agent + 定时任务 + 消息网关 | 定时 tick／消息指令／桌面会话 | 智能、交互入口丰富、可解释；与既有规则天然映射 | 启动成本高；需分阶段验证；存在误操作风险 |
| B. 脚本流水线 | 零 LLM 检查与修复脚本 + 系统定时任务 | 系统级 cron | 启动成本低；零 LLM；可控 | 无交互入口；脚本逻辑双源；与 LLM 操作对齐不自然 |
| C. 完全人工 + 偶尔外部代理 | 按需触发 | 命令入口 | 简单 | 没有自动化层；规模上来后无法维护 |

**决定**：采纳 A，但**分阶段落地，每阶段独立可验证、可回滚**。阶段总览：

1. 阶段 0（基线）：工作目录配置与 ADR 归档；
2. 阶段 1（skill 固化）：skill 只放指针与核心操作清单，不复制规则正文；
3. 阶段 2（定时监听 raw）：短周期 tick，只推到 `pending_review`，不执行 approve；
4. 阶段 3（定时重建索引）：长周期 tick，只追加或更新条目，不删改用户自定义分组；
5. 阶段 4（消息触发）：消息网关指令分发，approve 必须二次确认；
6. 阶段 5（定时化 lint）：长周期 tick，输出写日志，不自动修复。

**依据**：消息侧的入口是真实工作流的一部分，脚本流水线没有这一层；核心操作都是 LLM 任务，常驻 Agent 天然对齐，脚本方案反而双源；零 LLM 检查工具可被两条路径共享，不重复建设；分阶段加每阶段独立验证满足“短时间内可暂停全部”的硬约束，符合可逆原则。

**配套约束**：

- **approve 永远不自动执行**，实现中必须硬编码“必须见到人工确认标记才允许从 `pending_review` 迁移到 `processed`”；
- 监听脚本输出必须稳定：只输出纯文件路径与流程状态，不输出时间戳等额外元数据；
- 定时任务连续失败时自动暂停该任务并单条通知，不写日志，避免噪音循环；
- 新建定时任务默认不启用，首次由用户在终端显式触发，确认符合预期后再恢复；
- 不破坏 prompt 缓存：会话中只注入方案指针与摘要，不内嵌知识库全量内容；
- 不动知识库目录结构与文件命名；不动规则正本；不动凭据文件；不动会话配置表中已固化的模型配置字段。

**消息交互**：消息指令前缀对应五个子命令——ingest 走定时触发逻辑；approve 列出当前 `pending_review` 素材并等待人工二次确认；query 与 inspool 走对应核心操作；lint 走定时化 lint。

**与已有 ADR 的关系**：继承 ADR-0001（不得把 raw 状态搬出 frontmatter）；继承 ADR-0002（自动生成内容默认中文）；不创建新的语义层——只在自动化层落座，不改目录结构、不改既有规则。

**后果**：五类核心操作获得自动化入口，维护负担不随规模线性增长；代价是新增定时风暴、误批准、索引漂移三类风险，以及 skill 必须随规则演进而更新（以“skill 只放指针、正文每次重读”缓解）。

## 七、阈值与误报控制

内容页较少时，部分图拓扑检查会产生噪音，因此检查类命令设置激活阈值，未激活时跳过并提示当前统计值。

### 7.1 链接密度检查

仅当同时满足时启用：

- 内容页总数 ≥ 20（内容页 = 来源页 + 实体页 + 概念页 + 综合页下的 Markdown 文件，排除占位文件、索引、日志与元信息文件）；
- 平均出链数 ≥ 1.5。

### 7.2 图拓扑感知检查

仅当同时满足时启用：

- 图谱文件存在且解析成功；
- 内容页总数 ≥ 20；
- 边数 ≥ 1.5 × 节点数；
- 度数 ≥ 2 的节点比例 ≥ 40%。

### 7.3 数据来源与标识口径

健康检查默认只读，在统计结果中提供上述数值；写标志需提供库外私有状态目录并经执行门禁。图谱的节点标识为当前知识库相对路径（不含扩展名），是随目录重建的派生标识，**不应写回知识页当作永久语义 ID**。边的关系类型保留正文、证据与主题三类，一对页面计一条有向边。阈值统计只计内容页之间的边，导航类节点单列，不混入统计口径。

## 八、反模式

- 在知识页里直接堆大量裸露 URL；
- 只在正文写结论，不给任何本地来源链接；
- 只在 frontmatter 写关系，但正文没有任何显式双链；
- 把每个微小 claim 都拆成独立页面，导致图谱碎裂。

## 九、查询示例

以下为关系查询的典型形态，路径按实际知识库根目录替换：

```dataview
TABLE file.link AS 页面
FROM "<知识库根目录>/wiki/synthesis"
WHERE !supports OR length(supports) = 0
```

```dataview
TABLE file.link AS 页面, contradicts AS 冲突来源
FROM "<知识库根目录>/wiki"
WHERE contradicts AND length(contradicts) > 0
```

第一条找出没有证据支持的综合页，第二条找出存在冲突来源的页面。查询目录应针对顶层类型目录，以兼容使用者自建的分类子文件夹。
