## 1. 用户已确定的原则

1. 只维护一份设计文档，不再维护私人版与公开摘编版。
2. 迁移优先保证设计信息完整，不以压缩篇幅、文件数量或减少目录为目标。
3. 背景、需求、备选方案、选择与否决理由、契约、约束、审查问题、修复过程、历史状态、未决问题和证据定位均属于设计信息。
4. 凭据、私人原文、知识页、课程正文、个人学习记录与真实模型响应不公开。混合文档只处理具体私人片段，不整段或整篇删掉相关设计。
5. 原工作区保留备份，迁移完成后不继续在那里维护第二套设计。

执行范围：设计清点与迁移、设计导航、框架使用说明、必要的发布政策说明、公开文件清单和迁移记录。允许修复 README、CLAUDE.md 等错误入口说明。现有检查工具作为辅助使用，不开展通用解析器、测试框架或完整性平台开发。不得继续实现学习 Agent 功能、改变运行时业务行为、放宽私人内容保护、修改 AGENTS.md 规则、部署服务或发起真实模型调用。

## 3. 先固定基线，不继承旧计数

开始时记录目标 HEAD、当前分支、远端和 `git status`，分别记录目标暂存区及工作区已有修改。旧方案可能已经暂存，不能 reset、覆盖、撤销或夹带与本任务无关的修改。对将修改的文件保存原字节备份到被忽略的本地迁移记录目录，并记录其索引版本；不要把备份加入白名单。

记录源文件相对路径、大小和 SHA-256；迁移前再核对源字节是否变化，发生变化仅重新审核受影响条目。不要遍历整棵运行环境来生成无关的数十万文件清单。

候选范围必须递归覆盖：

| 范围 | 清点方式与目的 |
| --- | --- |
| `docs/design/*.md` | 包含已有目标同名文档，核对被裁剪的章节，不只是新增缺失文件 |
| `docs/design/research/**` | 包含研究笔记、复审、选型报告、证据索引与关联脚本，不能仅枚举 Markdown |
| `docs/design/archive/**` | 只读评估其中的旧设计、否决路线和版本演进；不得因目录名为 archive 而跳过设计信息 |
| `docs/design/evidence/**` | 先清点目录与说明，再按设计引用读取；识别独有设计判断、反例和修复原因，不整包复制运行快照 |
| `tools/**`、`patches/**` 的说明文档 | 恢复能力边界、接口说明、安装/验证前提和入口映射；代码和补丁不默认覆盖 |

`.git`、依赖包、缓存、数据库、模型请求和备份不作为批量扫描对象。运行目录仅在具体证据引用需要时定位读取。不能宣称未检索的所有私人存储均已审查。

输出 `design-migration-inventory.json`（本地、忽略）：逐文件记录来源摘要、类型、去向、处理状态、理由和依赖。候选状态至少包括：`preserve`、`merge_with_mapping`、`extract_design`、`exclude_private`、`exclude_non_design`、`blocked`。没有被分配状态的候选数必须为零；`blocked` 未解决不得宣称完整迁移。

## 4. 完整性如何落实

### 4.1 按正文迁移，不做摘要替换

以源文档完整正文为起点，与目标同名文档双向比较。保留目标新增的有效设计与独立仓库适配，不直接拿源版本覆盖目标。冲突保留两种主张及时间/版本，不静默择一。

默认保留原文件名和相对组织。可在目录中增加「当前设计／历史演进」标签，不为整理而集中改名。跨页合并仅在确有重复时做，并保留原位置到新位置的逐项映射。

必须逐项覆盖：

- 问题、触发条件、目标与不做事项；
- 方案比较、成本、否决理由和最终选择；
- 数据所有权、接口、Schema、状态机、权限与批准边界；
- 失败场景、反例、幂等、恢复、预算和兼容约束；
- 审查发现、是否修复、修复理由和剩余风险；
- 实施顺序、依赖、验收标准、未决问题；
- 原日期、版本、历史结果及对应证据定位。

不是只核对二级标题：表格行、代码块、列表中的契约和数字同样需要覆盖。不得使用「包含用户名／路径／反馈词就删整行或整段」的过滤器。

### 4.2 差异与映射记录

生成本地 `design-migration-map.json`：以源摘要绑定条目，记录源小节或稳定片段 ID、目标路径/小节、处置及理由。原样保留部分可按连续范围登记；所有删除、替换、合并与提取必须分别登记。

每个源小节均有去向，且每个删除/修改 diff hunk 均有解释。隐私替换不得把被删的真实值复制进公开报告。源文档与目标各自新增的独有设计都纳入核对。

优先复用现有清单、映射、Git diff 和简单只读检索核对路径、摘要及差异；内容审核判断设计含义是否等价。不为本次迁移新建完整性检查平台，原样保留的连续内容可以合并登记。标题覆盖率、字数接近、哈希和 LLM 自报均不能单独证明语义完整。

发布 `docs/design/migration-summary.md`：仅列已迁移的主题、目标入口、处理类别、必要限制及未公开证据范围；不公开私人文件名、原句或细粒度私人清单。完整核对记录留本机，不成为另一份持续维护的设计版本。

## 5. 具体内容处理规则

| 内容 | 处理 |
| --- | --- |
| 通用设计、备选路线、被推翻的结论 | 保留正文与版本关系；旧结论标记历史，不删除其推理 |
| 厂商/模型/公开项目名、公开提交与 API 名 | 保留准确名称；不要无依据改名或去掉来源归属 |
| 本机路径、用户名、临时目录 | 改为配置参数、相对路径或明确占位符，保留命令语义；覆盖 Windows 各盘符、反斜杠和 Unix 用户路径 |
| 来源项目为私人项目的例子 | 保留设计问题和约束，使用通用对象名；映射记录说明例子做了抽象，不冒充原始案例 |
| 用户反馈与试学结果 | 保留其提出的问题、需求和设计影响；个人身份、私人原话和学习记录不公开。无法抽象且不可替代时，暂停该条并说明缺口 |
| 测试数字、token/费用、基线摘要 | 属于设计依据时保留原数值和测量口径、版本；不公开对应私人请求正文。区分历史报告记载与当前复测 |
| 凭据、私人原文、真实模型响应、配置/账户信息 | 不进入公开仓库；只提取必要的通用设计事实，不能以字符串扫描零命中证明无隐私 |
| 上游源码摘录与研究材料 | 保留来源与固定版本；检查许可和再分发范围，不搬运上游完整副本；过长摘录以精确定位加分析替代 |

一份文档混有私人片段时，其他设计仍必须迁移。确有无法公开的设计信息，记录受阻的具体类别并交给用户决定；不得将其悄悄算作已完成。

## 6. 历史状态与证据链

不再使用「公开摘编」头部。保留有效 frontmatter 与一级标题；从正文标题或 frontmatter 的 title 获取标题，不能把第一行 `---` 当标题。

历史文档可增加短说明：原设计日期、适用版本、后续替代文档、证据可用性。不要给所有文档编造相同状态，也不要把历史的已通过改写成今天已验收。

证据处理分四类：

1. 仓库内可公开材料：发布审核过的最小必要材料，并使用真实链接。
2. 公开上游：保留仓库 URL、完整提交 SHA、文件路径和可定位行号；能核对时使用固定提交链接。保留证据 ID 与判断的映射，不能只写「项目名＋短 SHA」。
3. 私人证据：不发布附件；保留必要结论、日期/版本与「证据未公开，无法由本仓库独立复核」标记。不得把另一篇设计文档伪装成同等实测证据。
4. 已丢失或无法确认的证据：明确标记，不能伪造计数、通过回执或可复现性。

研究报告引用 JSON 索引和审核脚本时，逐项评估是否能作为通用研究材料发布；不能只发布 Markdown 然后声称全部证据已可复核。若不能发布，给出证据覆盖范围及缺口。

## 8. 与本次资料直接相关的核验

检查服务于内容迁移，采用现有工具加人工核对，不要求检查器支持全部 Markdown 语法。

1. **完整性**：对照候选清单和源/目标差异，确认独有设计都有去向；重点审阅删除、替换和合并内容。复用已完成的记录，不因阶段切换反复全文审查无变化文件。
2. **隐私**：审核实际准备发布的文件及变更片段，确认无私人知识正文、个人学习记录、账户凭据和真实运行数据。保留私人目录硬拒绝及白名单保护；扫描零命中不能替代内容审核。
3. **可读性**：确认真实标题、导航入口及本批实际使用的链接可用。历史证据不公开时明确标注，不要求补造证据或恢复历史执行环境。
4. **发布内容**：交付本地结果时可检查工作区；提交前须核对最终暂存文件列表、白名单和暂存正文，不能以磁盘上存在私人文件证明链接在发布后可用。
5. **工具限制**：现有检查器不能可靠处理的链接或锚点，逐项人工核对并记录，必要时改为可读的常规链接。无需先修复通用解析能力。不得把未识别语法算作已自动通过，也不得关闭检查或扩大豁免来绕过真实问题。

若现有检查器实际阻止提交，先完成并交付资料整理，记录具体阻断；优先作不损失信息的文档修正。确实必须改代码时，另列最小改动及理由，不自行扩成工具开发任务。资料整理完成与发布完成分别报告。

只修正文档时不跑学习 Agent、模型、课程生成、初始化或全量运行时回归。已有测试结果保留原日期和适用版本，不冒充本次复测。

## 9. 执行阶段与交付物

### S0：冻结与盘点

确认路径/远端和已有修改；备份待改文件；清点第 3 节范围，产出完整候选清单、源摘要、依赖图、目标现存独有内容。记录实际数量，不继续引用旧方案的 44/59 等数字。

退出条件：清点范围与排除规则可复核；所有候选有初步处置；旧源文件及原有用户修改受保护。

### S1：必要的文档基线修复

核对第 7 节标题、入口、政策与框架说明。已有修复直接复用；仅处理仍影响资料保留和阅读的问题，不继续扩展发布检查器。

退出条件：影响本次内容的文档缺陷已修正或已明确记录，阶段差异可审阅。检查器的通用语法兼容问题不阻止进入 S2。

### S2：完整迁移

按主题组织工作，建议顺序：总体目的/维护门禁 → 上游选型与原始研究 → 学习底座及数据交接 → 知识准备/准入/入库 → 课程与出题/扩展 → 成本与集成审查 → 历史演进和未决问题。此顺序只用于执行和导航，不成为遗漏其他文档的筛选规则。

每批执行：读取全文 → 合并两侧独有信息 → 最小隐私处理 → 保留证据定位 → 填写完整性映射 → 审阅变更块 → 核对本批隐私和实际链接。不能因研究笔记重叠、篇幅较长或含 main-executor 名称就整份排除；合并必须证明全部独有信息已有去向。

退出条件：每批映射完整、隐私审阅完成、所有新增文件登记。依赖尚未迁入时使用未提交候选或合并依赖批次，不关闭门禁来提交断链。

### S3：导航与整体核验

重写设计入口：当前设计、历史演进、研究依据、操作说明分别可发现。每份设计至少有导航入口；每个已替代方案标明后续关系。更新根 README、PUBLICATION、MIGRATION、VALIDATION 与白名单。

输出公开迁移摘要和本地逐项差异报告，核对全部源候选及目标独有内容，没有未解释删减。原目录保留现有文件作为历史来源，并保留迁移指针；不删除或整理源文件，不清理私人文件、不重写原历史。

### S4：交付与发布

有提交授权时仅提交目标仓库本次范围，可按主题分提交；只有有发布授权且所有阻断关闭后才推送指定远端。先检查远端新增提交，不覆盖其他 Agent 的工作。推送后核对远端 HEAD 等于实际交付提交，并重新确认私人目录没有进入可达历史。

## 10. 完成标准

| 维度 | 必须交付的证据 |
| --- | --- |
| 单一正本 | 独立仓库是唯一维护入口；没有另一份持续编辑的私人设计正文 |
| 文件覆盖 | 候选清单全覆盖；blocked 和未分类为零；排除均有内容理由 |
