## 2. 已确定的原则与尚未决定的机制

| 已确定 | 说明 |
| --- | --- |
| 资料先暂存、明确要求后整理 | 不是每个链接都生成课程，也不因课程生成就自动入库 |
| 来源与正式知识长期独立 | 学习应用是消费者；生产方需能访问已有知识 |
| 外部 Agent 承担开放式搜集、核验与整理 | 内部应用负责学习交互；允许使用强模型，主要复用成熟 harness |
| 学习事实、模型判断、用户声明分开 | 学习结束、独立掌握、正式入库不混用 |
| 界面与 Agent 共用业务入口 | 传输可选 CLI/HTTP/MCP，共用逻辑不等于共用权限 |
| 本地单用户优先、工程边界清晰 | 共享目录与产品数据库均可；不提前做 SaaS、微服务或插件平台 |
| 复用优先，按实际职责计价 | 完整应用、SDK、源码、设计思想分别说明；不拼接所有项目 |

待决定的是学习主体验与底座、实际数据交接、首个可用闭环。**OpenMAIC 是固定课堂候选，不是既定唯一赢家。** DeepTutor 的 Book/typed blocks、CLI/SDK 与模块化形态必须纳入；不能再用“没有课程化产物”或叠加全部可选前端成本排除它。

## 4. D1：学习体验与底座选择

### 4.1 使用相同的情境比较

至少比较完整 OpenMAIC、满足需求的 DeepTutor 模块组合（包括所需 Web，不把 CLI-only 当有网页）、以及仅在两者存在实质缺口时的局部适配方案。Lattice/Open Notebook/Kotaemon 作为产品原则和局部机制参照，不要求再部署它们。

以同一小组自有/公开技术资料为静态情境，覆盖两种入口：

1. **结构化学习**：用户明确要求整理资料 → 查已有知识 → 生成可查看的学习内容 → 追问 → 答题 → 关闭后恢复 → 导出证据给外部 Agent。
2. **围绕来源学习**：打开一份资料并问一个局部问题 → 支线解释/练习 → 回到原位置 → 保存有价值的结果；说明是否必须先生成整门课。

第二种入口用于判断系统是否被课件形态不必要地锁住，不代表本期必须同时实现两个完整产品。用户界面控制需求按功能拆开：需要自己的入口、自己的组件、还是上游界面已可接受；不能把任何 UI 改动都估成重写整个 harness。

### 4.2 每个候选交出真实组成

- 实际入口及调用链，使用哪条教学、评分和状态路径。
- 必装与可选模块、前端、数据库/后台任务、模型与本地重依赖；源码全量环境和最小适用组合分开。
- 产物类型、持久状态、版本和来源定位，以及外部 Agent 可读的具体接口。
- 直接采用、配置、普通适配、上游补丁、真正自建分别计工作量；已有代码行数仅作范围线索，不作为工期或运行性能证明。
- 缺口是否能通过上游已有扩展点解决；是否新增第二套 Agent/学习状态或相同职责的服务。
- 模型调用的静态组成、可关闭开销与软/硬限制，不编造费用或省 token 百分比。

### 4.3 决策产物与完成标准

给出一个明确推荐、适用的主体验、未选方案的真实代价，以及哪些条件会改变推荐。使用事实矩阵与理由，不用未经验证的加权分数伪装客观结论。

至少对四个决定推荐的点提供固定提交、路径/符号和适用配置：内容生成、教学交互、答案持久化、机器读取结果。既有证据可直接引用；新观察可写紧凑定位，不要求增加证据条数。运行未知可保留，但若它能改变推荐，须给出最小定点验证方式，不能要求先完成整个产品适配才能选型。

## 5. D2：数据、操作与交接契约

### 5.1 对象、写入责任与寿命

对以下对象列出稳定身份、拥有者/写入者、实际存储/读取方式、修改与删除语义、引用和缺失处理：

- 原始来源与版本、提取物、来源摘要；正式 accepted 来源页仍沿用 wiki/sources。
- 课程/交互书/阅读活动及其内容身份；区分可编辑工作内容与只读学习输入证据。
- 学习尝试、实际答案、原模型 verdict、兜底与失败；区分实际事实和派生判断。
- 用户声明、导师估计、独立评估，以及跨活动/专题/当前会话的作用域。
- 交接包、快照、可重建索引和正式知识候选。复制的证据不等于第二份可独立编辑的真值。

逻辑身份不依赖可移动文件路径，也不直接等同上游 materialId/stageId/bookId。课程/来源实际内容版本与 runtime schema 版本分开，不能把变更计数当历史内容库。

### 5.2 应用操作与实际映射

按需要列出资料收集/准备、知识查询、学习活动发现/打开、基线固定、学习结果读取/导出、知识候选提交等应用操作。明确由项目、外部 Agent 或上游应用中的谁提供，实际通过什么入口完成；不是要求本期全部自建 API。

页面、CLI、HTTP、未来 MCP 共用这些业务语义，正式写入/批准继续走现有授权。若上游 GUI 能做而机器接口不能做，要明确列为缺口；不要用 UI 功能证明外部调用已可用。

### 5.3 一份契约与三个静态映射例子

提供最小字段示例和上游→项目字段对照，包含身份、内容绑定、证据出处、原始记录、评分来源、派生标签、覆盖与采集位点。缺字段允许明确 unknown/partial/unsupported，不新增模型调用“恢复”历史。

在文档内给三个小例子即可，无需建立 fixtures 平台：

1. 正常提交与结果读取，同一素材被两个活动复用。
2. 评分服务失败/结果不完整：逐题标模型、确定性或本地兜底，保留原值，不因 completed 就判成功。
3. 学习后内容发生变化，或多次读取之间变化：拒绝错配/标未知，说明历史输入和导出一致性如何表达。

再说明重复请求、身份不一致、来源缺失、重启后结果读取、聊天保留边界的处理。跨 session 的 seq 不当全局序号；没有辅助日志不推独立作答。

### 5.4 完成标准

可从示例回答“外部 Agent 实际收到什么、能判断什么、不能判断什么”，每个必要字段有真实上游来源或明确新增责任；不需要先实现适配器/数据库。方案既不能强求上游原生拥有全部字段，也不能隐藏补齐证据的工作量。

## 6. D3：首个可用闭环与工程边界

依据 D1/D2 推荐一条主流程，写清输入、界面、追问、答题/学习行为、恢复和向外部 Agent 交接的可见结果。

必须交代：

- 本期支持哪些活动、题型、资料类型；哪些功能仅展示、仅部分导出或不支持。
- 需要的组件与上游依赖、项目模块边界、模型调用入口、资料工作区与正式 wiki 的界线。
- 谁保存生产回执和学习前证据，谁读取/导出；用户在上游直接修改时怎样避免静默错配。
- 预算/并发/重试/取消与 usage 的已有能力、真实缺口；用量日志不当价格账单或硬预算。
- 运行与数据备份、固定版本及升级兼容的最低要求，避免只备课程文件而丢学习状态。
- 后续 UI、检索、学习画像、PBL/执行环境等扩展的接口位置与触发条件，不提前实施。

产出“直接复用 / 配置与 SOP / 薄适配 / 需要上游补丁 / 后置”清单，并给风险和粗粒度成本。完成标准是形成一条职责完整、可独立验收的首个闭环；**本轮仅写未来实现时如何判断完成，不执行流程测试，不拆到函数级开发任务。**

## 7. 合并与验收

`design-summary.md` 保持简短，汇总：所选主体验与底座、实际组件、数据/操作边界、首期覆盖、已排除的复杂度、决定性证据、剩余未知、需要用户选择的真正产品分歧。D1–D3 的详细内容不复制三遍。

收敛后同步 [总体设计](research/upstream-learning/architecture-proposal.md)、[验收状态](research/upstream-learning/acceptance-request.md) 和设计索引。旧 OpenMAIC 路径中的机制若不再采用，标明参考方案，不能仍作为本期必装组件。

验收重点：推荐与用户目标一致，底座能力已定位，必要交接字段可解释，工作量没有藏在“薄”字里，首个闭环范围有限，未来扩展没有迫使现在增加平台。缺运行数据不是设计缺陷；源码误读、真值冲突或关键接口缺失才需要修订。

执行者提交设计，本对话主 Agent 复核关键结论；简单文字/定位问题直接修，避免为了文档小错不断往返。所有决定收敛后才另写实施任务书，不自动开始开发。
