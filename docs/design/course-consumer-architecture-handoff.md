**推荐路线（一句话）**：以 OpenMAIC 的课件契约与存储契约作为“生产方 → 消费方”的稳定边界——**依赖**其可发布的 npm 包 `@openmaic/dsl` / `@openmaic/storage`，而不是 fork 整个 Next.js 应用；以 DeepTutor 的 `deeptutor/learning` 域作为学习状态**判定与推进**层的来源；两者之间用一个薄的课件消费端连接。

**明确否决三条**：Lattice 作底座（无任何对外接口，且 Vault 启动即对整个工作树 `git add -A` 并提交、还会改写用户 `.gitignore`）；open-notebook-mcp 作集成层（JSON body 打到 `Form(...)` 端点、该用 `/api/sources/json` 却没用，失败是静默降级）；Kotaemon 检索栈（其检索／重排／引用三项**均已被首选产品覆盖**，属重复而非高成本）。

**本轮复查发现的 4 处更正**（详见 `acceptance-request.md` §3.4，均已写回四份产物）：

1. “OpenMAIC 的学习状态只有记录流”**过粗**——它有完整的学习者运行时层（状态梯、kind 分类、`learnerKey` 分区、CAS 追加、409/404 错误语义、确定性 `quizAttemptId`、含 `/runtime/learners/merge` 的完整 HTTP 面）；真正缺的是**掌握度判定、目标推进、定量/定性分离、通用导出**。
2. **OpenMAIC 的 SDK 边界被初稿漏掉**——两个包是 npm public 可发布包，storage 唯一 runtime 依赖只有 dsl，且自带独立 HTTP 服务端与版本化 schema 迁移。**净效果：适配面从“改造应用”缩到“实现两个接口”。**
3. **OpenMAIC 对材料不做 RAG**——`lib/rag/` 有实现但主应用零 import，唯一 provider 无向量；这改变了“是否要另建检索栈”的判断。
4. **open-notebook 一次问答是 1+N+1 次模型调用**，不是一次；成本口径必须按 N 计。

**净效果：推荐路线不变，但两件实施方案变了**——OpenMAIC 的 runtime 契约从“抄”改为“依赖”；“学习交接包”确认上游没有，**必须自建**。

**下一步门槛（按此顺序，前一项不成立则后项不必做）**：A10 确认两个 npm 包能真正被依赖 → A1 只实现 `RuntimeStore` + `DocumentStore` 两个 SQLite 后端 → A2 移植 `deeptutor/learning`（切 knowledge 依赖）→ A8/A11 交接契约与导出层 → A12 材料侧检索链（**可后置**）。

## 2. 用户已经澄清的目标与动机

- 用户希望拥有自己的可视化学习应用，能够查看课程、学习、提问、答题并保存进度；未来知识库也可有独立界面和接口。
- 外部成熟 Agent 擅长开放式资料搜集、检索、核验、整理与复杂任务，尽量复用其工程能力和工具生态。
- 内部 Agent 可以直接调用优秀模型的 API。内部能力短板主要是自建 harness 的上下文组织、检索命中与执行工程，不能把它等同于“模型推理能力弱”。
- 复用已有订阅不是必要限制，不应据此排除内部 API 模型。
- 用户倾向复用成熟项目的设计和实现，先前已明确考虑 Lattice；不希望为了学习交互重新开发完整通用 Agent。Lattice 尚未被确定为最终底座。
- 先考虑单机、本地、单用户，外部 Agent 与内部应用能访问同一目录，以降低传输、部署和协作成本。
- 设计要职责明确、便于后续扩展和优化；当前处于设计讨论阶段，可以调整结构，不必用虚构的版本包袱阻止合理设计。

## 3. 已认可的三方职责方向

| 领域 | 核心职责 | 交付或消费对象 | 自己维护的状态 |
| --- | --- | --- | --- |
| 资料工作台／外部 Agent | 接收资料；用户指令后检索已有知识、去重、核验、归类；按需要准备课件或知识候选 | 输入资料、课件包、知识候选 | 收集记录、整理批次、处理决定、生成记录 |
| 课件消费应用／内部 Agent | 展示课程、讲解、追问、练习、补讲与学习反馈；由程序可靠保存学习状态 | 消费标准课件包，输出学习交接包 | 答案、评估、进度、学习记录与完成状态 |
| 知识库与维护入口 | 提供已有知识；按现有规则审查、应用和归档正式知识 | 提供检索结果，接收受控候选 | 知识版本、来源关系、维护事务与归档记录 |

这是一种生产与消费分工，不要求三个服务进程或三套部署。共享契约和必要工具即可，不默认建设跨三方的统一业务数据库或全局调度平台。

**课件消费者的独立性判据（建议作为选型验证条件）：**只提供课件根目录和模型 API 配置，不提供知识库路径、MCP 或外部 Agent，也能发现课程、学习、答题、重启恢复、结束并导出交接。

## 4. 用户要求的实际使用流程

1. 用户白天向外部 Agent 发送链接、文件或想法，先进入资料工作区，不自动把每条链接变成课程，也不默认立即入库。
2. 用户晚上或其他时间明确要求“整理今天的资料，准备入库”等，才开始相应整理；“整理”“生成课程”“准备入库”的具体授权范围仍需在协议中写清。
3. 外部 Agent 可读取现有知识库，识别已知、重复、新增、冲突及待确认内容；按主题和学习目标组织，而非机械地一链接一课程。
4. 对需要学习的内容生成标准课件包并交付。参考保留、重复、暂缓等资料也要有处理记录，不能因没生成课程就默认可以绕过既有学习门禁入库。
5. 用户打开学习界面，看见可学习课件，点击后开始。内部 Agent 消费课件并负责学习交互，程序保存实际答案和状态。
6. 学习结束输出交接，外部 Agent 再结合原始资料和已有知识准备知识候选；正式入库与 raw 归档继续遵守 AGENTS 和受控维护流程。

外部 Agent 不必常驻；MCP 可提供操作入口，但不能据此假设能自动唤醒外部 Agent。最初可由用户明确发起整理与后续入库。

## 5. 课件目录思路与建议约束

用户提出按“待处理／学习中／学习完成”组织课件，一个课程一个独立文件夹。方向已认可；以下是需在设计中具体化的建议，不代表文件格式已经发布。

- 粗粒度生命周期以所属目录为准；课内详细进度由消费应用维护。不要再用另一份可独立修改的数据库状态复制目录生命周期；界面索引可以重建。
- 发布前先在生产方暂存位置完成并校验，再交付到待处理区，避免消费者读到半包。具体发布原子性、文件占用和异常恢复仍需验证。
- 用稳定课程 ID 与版本识别课程，不能拿绝对路径作为身份；资源尽量包内自足，使用相对引用。
- 交付后的课件内容冻结；学习记录与生成内容分开保存，防止外部 Agent 后续整理时改掉正在学习的内容。
- 消费端负责领取、阶段迁移及学习状态；生产方不同时搬运已交付课程，下游不改写学习记录。单机仍需处理重复导入、多个窗口、写入中断和移动失败。
- “学习完成”“掌握达标”“知识候选通过／正式入库”是三个不同结论。保留按目标的答案与评估，不把一个完成按钮作为全部证据。
- 学习交接应包含课程版本、学习目标、必要的答案／评估证据、未解决问题与来源指向；默认不导出完整私人对话。
- 下游回执建议绑定课程版本和交接摘要，重复消费应幂等。入库失败不应把已完成课程退回或覆盖学习状态。
- 固定课件契约应控制为最小必需内容：课程身份、目标、材料与来源、教学内容或教学组织线索、练习／评估要求、资源清单。具体字段、引用粒度和扩展方式待选型后确定。

## 6. 与现有工程的关系与未决边界

现有 S0／S1 为协议、持久任务循环、账本、受控 Executor 与恢复等打了基础；它们不等于完整课程系统已经实现。不得为了复用既有 Runtime 而强迫三个领域共用全部运行时、状态和数据库；也不能未经审查就删除已有授权、预算、恢复和正式文件接受保证。

现有设计倾向把学习与入库放在一条门禁链上。本轮提出独立课件消费者，后续必须明确：谁产生可信 Assessment、如何绑定课程与证据版本、下游如何验证学习结果、人工确认承担什么作用。外部成熟 Agent 可读文件不等于其写入天然可信，目录共享也不等于所有参与方拥有相同业务写权限。

当前课程示例 `lessons/0001-follow-a-candidate.html` 与 `assets/teaching.js` 曾定点查看：答题反馈主要在页面内，未构成可靠的答案持久化和外部 Agent 回传链路。不能把示例页面当成新方案已经落地的证据；后续检查以当时代码为准。

## 7. Lattice：已做源码阅读的线索

> **状态（2026-11-09 更新）**：本节线索**已在本轮源码研究中完成定点核实**，结论是 **Lattice 作为底座被明确否决**——它没有任何对外服务接口，且 Vault 每次启动会对整个工作树执行无路径限定的 `git add -A` 并提交、还会改写用户 `.gitignore`。本节保留为线索存档，不再作为候选。**唯一被采纳的部分**是 `lattice/web.py` 的 SSRF 防护设计（解析域名后拒绝回环/链路本地/组播/私有网段，含 fake-IP 段例外处理）。详见 `research/upstream-learning/report.md` §8 与 `architecture-proposal.md` §4 路线 6。

- 项目：[vimalinx/lattice](https://github.com/vimalinx/lattice)，MIT。已克隆到临时目录并阅读源码；没有安装依赖、运行应用或执行其测试。
- 本次研究固定提交：`42579b8d4190f0db2f139ca9384d3d438dc56112`。
- 本地研究目录：`<本机临时目录>`。临时目录可能被系统清理；若丢失按提交定位，不把临时路径作为产品依赖。
- 它有自建 Agent 运行循环，调用外部基础模型，并非自己训练模型。Tutor／Flash／Coach 等是共享引擎的角色配置。
- Qt／PySide6 WebEngine 承载前端，QWebChannel 连接 JS 与 Python；`lattice/providers.py` 的 `ApiWorker(QThread)` 处理模型请求、流式响应与工具循环。
- **不必先解除 Qt 线程依赖。**若选择桌面应用，保留 Qt 是合理方案；若必须普通浏览器访问或无界面服务，再评估分离后端。用户已追问过这一点，不要把“模块化”解释为“必须重写 Qt”。最终交付形态尚未确定。

> **状态（2026-11-09 更新）**：本清单**已执行完毕**——七项逐条落到了 `research/upstream-learning/report.md` 的五条处理链与 `architecture-proposal.md`。逐项落点：①消费独立性→§5.1.1 与提案 §5；②课件契约→报告 §3.1、提案 §5.3/§5.4；③状态与恢复→报告 §3.3、提案 §5.5；④教学证据→报告 §3.3（DeepTutor 定量/定性分离）；⑤上下文和成本→报告 §3.4/§6；⑥副作用与扩展→提案 §5.2.1（重复存储/两套 Agent/多余工作台/全局运行时逐项回答）；⑦工程可维护性→提案 §4/§8。**下面的原始清单保留存档。**

先围绕下面问题定点查源码，形成有证据的对照，再决定是否修订总体方案。不要先搭插件平台或迁移现有工程。

1. **消费独立性：**能否导入外部生成的课件？是否强依赖自带生成 Agent、知识库或数据库？无外部 Agent 时能否独立完成学习？
2. **课件契约：**教学内容、练习、答案／评分标准、资源、来源定位如何表达和版本化？既能静态渲染又能动态辅导吗？
3. **状态与恢复：**谁保存实际答案、评估和完成状态？刷新、重启、中断、重复请求及模型失败后能恢复到哪里？
4. **教学证据：**反馈如何绑定具体目标、题目、答案和版本？是否能区分听完课程、做完练习与理解达标？
5. **上下文和成本：**每次模型调用读入哪些资料？有没有有界检索、摘要和调用／token／时间上限？检查实际调用链，不能只读功能宣言。
6. **副作用与扩展：**能否限制写入课件及私有学习状态？如何输出交接？正式知识库是否能保持独立？Qt 桌面与浏览器方案分别需要改多少？
7. **工程可维护性：**许可证、依赖、Windows 单机部署、测试与升级边界如何？先确定少量必须改动，不把可选功能全部纳入。
