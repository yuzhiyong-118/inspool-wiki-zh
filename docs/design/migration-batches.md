## 三、怎么复核

12 个批次都是**独立提交 + 附注标签**，可以按标签逐步检查：

```bash
# 1. 看批次序列
git log --oneline --decorate f2cea87..main

# 2. 逐批查看该批次改了什么
git show --stat s2-batch-c
git show s2-batch-c -- docs/design/learning-book-i3-plan.md

# 3. 任取一个批次检出，检查该批自身是否自洽（无断链、无私人内容）
git checkout s2-batch-e
python -B tools/check_public_release.py --staged
python -B tools/health.py --json

# 4. 对比两个相邻批次，确认增量符合预期
git diff s2-batch-d s2-batch-e --stat

# 5. 独立复现「实例级私人痕迹」的扫描
python -B tools/check_instance_markers.py            # 当前工作区
python -B tools/check_instance_markers.py --commits  # 逐个扫未推送区间的每个提交

# 6. 相关测试
python -B -m unittest tools.tests.test_public_release_gate \
  tools.tests.test_public_release_syntax_matrix \
  tools.tests.test_public_workspace tools.tests.test_instance_markers
```

每个标签是**附注标签**，`git tag -n99 -l 's2-*'` 可读完整说明，里面写明该批内容与验证状态。

> 门禁读的是**该提交自身的暂存树**，所以每个批次都能独立通过，不必依赖后续批次补链。

逐项的源小节 → 目标位置映射留**本机** `.tmp/design-migration/s2-ledger-batch-a~k.json`，不随仓库发布；仓库内保留的是本篇、[迁移摘要](migration-summary.md)与[验证记录](../VALIDATION.md)。

2. **判据在形式层，泄漏在语义层。** 去重判据是「归一化后完全相同」，命中不了「语义等价但取值不同」的段落；抽象规则同样按句式匹配，漏掉表格单元格、括号内嵌等写法。
3. **抽样被当成全量。** 批次 I 的抽象只覆盖被点名的 20 份文档，「个人累计用量」这一类在别的文件里换一种句式继续存在。

**排查方法。** 换掉同源判据，用独立基准交叉：源侧逐行对照（私有源 13,434 份建索引比对公开侧）、实例标识普查（2,681 份证据与产物中抽出 2,960 个标识符形态取值逐个回查）、用量数字普查（区分绝对账本量与比例、计数、额度）、重复变体扫描（归一化相同但原文不同的段落对全库比对）。

**排查结果。** 重复变体扫描命中的 4 组逐条核对后均非缺陷（3 组是不同任务的允许路径与验收命令差异，1 组是同一文档内两个时点的基线哈希表）。标识符与用量普查确认 13 份文档仍有同类残留，已全部抽象为「见本机账本」或通称；本机端口改为「本机端口已关闭」。保留未改的边界与批次 I 同一判据（授权额度与暂停线、调用与门禁计数、发行物文件数与模块数、由账本推导的比例、上游公开统计与源码常量）。

**历史层同样处理。** 未推送区间的提交都带着这批数字，因此不追加删除提交，而是改写历史（首次改写前该区间共 274 处残留命中），删除 `refs/original`、清空 reflog 并回收对象。历史一共改写三次：批次 I 一次，批次 J 两次。**副作用要如实说明**：抽象规则回溯应用到更早的批次提交后，批次 J 的 diff 相对上一提交只剩少数几份文档，13 份内容文件的改动体现在父提交的树里——想看全貌请比对 `s2-batch-i` 与 `s2-batch-j` 两个标签之间的树。

**把验证交出去。** 排查脚本原本是本机临时文件，复核方拿不到也无法复现。因此把形态子集固化为 `tools/check_instance_markers.py`（配套 17 项判据测试），并写明它的三条局限。**工具立刻抓出了它自己那一轮的漏检**：第一次逐提交扫描就报出批次 A／B 树里 `LOCAL_USE.md` 仍写着「首题 1 次／3,653」——原因是先前的普查脚本按「五位以上数字」过滤金额，四位数带千分位被漏掉。这条本身就是「换验证基准」有价值的证据：**同源判据之间不会互相纠错，独立判据会。**

### 批次 K — 收尾三项

**一、受控扩展的缺陷状态被写成了当前待办。** [审查发现与修复机制汇总](evidence-findings.md)第五节原把三项实现缺口列为「未关闭」，实为三轮独立复审的历史发现：`release-04` 不通过（6 项阻断）、`release-12` 不通过（4 项新阻断）、`release-14` 通过（上轮四项全部关闭，原 R01–R07 继续通过）。已改写为完整的「发现 → 修复 → 后续复核」演进关系，补进原汇总缺失的 CE-R7／CE-R8，单列**三轮之后仍未关闭的三条**，并注明 `release-16`～`release-21` 属实现与部署、`release-21` 未做新的独立复审。

**二、提取类覆盖做了实测核对。** 以已发布的公开 Markdown 为语料，对 162 份提取类来源先测技术标识符落点、再对含设计判断的句子做语义级比对，定位到**两处真实遗漏**：上游研究笔记里约 70 条**源码级机制结论**未迁入（新增[上游源码级机制结论提取](research/upstream-learning/source-mechanism-findings.md)）；I2 探针的**三项核验口径教训**此前只有结论没有机制（补入汇总文档第三节）。其余来源的独有内容经逐份核对确认已落位。

**三、误覆盖的实情与原记载方向相反。** 原记载说私有 `wiki/log.md` 被覆盖且无 Git 历史可回溯。单独核查（逐文件字节比对 + 行级差异 + 回溯可用备份 + 波及面排查）的结论是**方向相反**：

| 项 | 原记载 | 实际 |
| --- | --- | --- |
| 受损的是哪一份 | 未区分，笼统写「私有 `wiki/log.md` 被覆盖」 | **两份都没受损**。私有工作区那份**较新**（601 行）；公开工作区那份**较旧**（573 行） |
| 差异方向 | 读起来像私有那份被改旧了 | 实际是**公开工作区那份停留在更早的状态**，缺批次 J 记录与 2026-11-17 凭据条目 |
| 差异规模 | 未给 | 私有比公开多 27 个非空行；公开独有 2 行，且那 2 行是**旧版本的事实陈述**，不是独有内容 |
| 能否回溯 | 「无 Git 历史可回溯」 | **可以回溯**。私有仓库历史里最后被跟踪的版本与当前版本逐行比对**零行缺失** |
| 波及范围 | 只提 `wiki/` | `raw/` 层 10 份文件**逐字节完全一致**，未被触及 |

所以真正受影响的不是数据，而是**副本不一致**：公开工作区跑 `tools/health.py` 读的是本地那份旧内容。已把公开工作区的 3 份陈旧副本按字节同步到私有当前版本（同步前旧副本备份在本机 `.tmp/design-migration/`），同步后两处 31 份逐字节一致、两处 health 结果一致。只动被 `.gitignore` 排除的本地副本，**不触及任何公开提交**。

## 六、已知限制与开放问题

- **未推送**。12 个批次都在本地，远端仍是 `f2cea87`。发布前请重跑门禁与 health，并核对 `git rev-parse HEAD` 与远端一致。
- **早期提交号已作废**。三次改写未推送历史后，旧号在仓库里已不可达。任何外部引用、审查记录或工单里出现的旧号都要换成标签。
- **工具能力的边界**。两个工具都不能可靠处理语义层面的泄漏；不能可靠处理的 Markdown 写法按人工核对逐项处理并记录，不以「工具未报」当作已通过。
- **提取类覆盖不是全量语义证明**。两轮实测定位到两处真遗漏并已补，但逐字比对识别不了改写式迁移——「已落位」的判断含人工成分。
- **旧工作区仍在**。原工作区保留为只读历史来源，其 `docs/design/public-repo-content-backfill-plan.md` 只是定位指针，不再维护正文。是否清理旧目录属于后续独立操作。
- **完成不等于验收**。本文与[迁移摘要](migration-summary.md)只说明做了什么与怎么核对的；设计内容是否被证明完整，需要人工按第二节逐项判断。
