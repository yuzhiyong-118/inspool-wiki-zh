# 设计迁移批次交接说明

本文写给**接手审查这次迁移的主 Agent**：八个批次各自做了什么、为什么这样做、怎么复核、以及哪些地方需要重点看。

迁移方案见[设计信息完整迁移与单一正本方案](public-repo-content-backfill-plan.md)，迁移的范围口径见[设计迁移摘要](migration-summary.md)。

## 一、怎么复核

八个批次都是**独立提交 + 附注标签**，可以直接按标签逐步检查：

```bash
# 1. 看批次序列与各批的公开文件规模
git log --oneline --decorate f2cea87..main

# 2. 逐批查看该批次到底改了什么
git show --stat s2-batch-c
git show s2-batch-c -- docs/design/learning-book-i3-plan.md

# 3. 任取一个批次检出，检查该批自身是否自洽（无断链、无私人内容）
git checkout s2-batch-e
python -B tools/check_public_release.py --staged
python -B tools/health.py --json

# 4. 对比两个相邻批次，确认增量符合预期
git diff s2-batch-d s2-batch-e --stat
```

每个标签是**附注标签**（`git tag -n99 -l s2-batch-*` 可读完整说明），说明里写明该批内容、验证状态与后续批次。

> 检查某个标签时注意：门禁读的是**该提交自身的暂存树**，所以每个批次都能独立通过，不必依赖后续批次补链。

逐项的源小节 → 目标位置映射留**本机** `s2-ledger-batch-a~h.json`，不随仓库发布；仓库内保留的是本篇与[迁移摘要](migration-summary.md)。

## 五、需要重点复核的地方

1. **逐小节合并的语义判断**。C–G 各批共 90 处「两侧都有但内容不同」的小节，行级并集是保守做法——不丢信息，但可能留下两段语义相近的表述。请重点看这 90 处的可读性，以及是否有应当只保留一侧却没判断出来的地方。
2. **批次 B 的 24 份依赖闭包**。它们因为被批次 B 的文档引用而提前发布，自身的设计内容按 preserve 处理，未做逐小节核对。
3. **提取类内容**。`wiki/meta/` 的通用规则、证据目录的复审结论、研究过程笔记的方法口径，都是从「不发布」的材料里提取后发布的，提取边界是否准确需要人工判断，工具无法证明。
4. **未公开证据的标注**。约 26 处引用标注为「证据未公开，无法由本仓库独立复核」。这类结论本身随正文发布，但复核依据不在仓库内。
5. **计数与状态的口径**。正文保留了原始验收计数与状态表述，靠文档头部声明「对应原文写作时点的环境」防止误读。

## 六、已知限制与开放问题

- **未推送**。八个批次都在本地，远端仍是拆分框架时的 `f2cea87`。发布前请再跑一次 `python -B tools/check_public_release.py --staged` 与 `python -B tools/health.py --json`，并核对 `git rev-parse HEAD` 与远端一致。
- **旧工作区仍在**。原工作区保留为只读历史来源，其 `docs/design/public-repo-content-backfill-plan.md` 只是 554 B 的定位指针，不再维护正文。是否清理旧目录属于后续独立操作。
- **工具能力的边界**。公开门禁覆盖暂存树可达性、凭据形态、标题与 frontmatter、锚点与越界路径；不能可靠处理的 Markdown 写法按人工核对逐项处理并记录，不以「工具未报」当作已通过。
- **完成不等于验收**。本文与[迁移摘要](migration-summary.md)只说明做了什么与怎么核对的；设计内容是否被证明完整，需要人工按上述第五节逐项判断。
