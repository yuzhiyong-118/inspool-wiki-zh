# 知识库重设计多维审查方案

## 1. 审查目标

判断当前重设计能否以可接受的用户负担、Agent 操作成本和长期维护成本，支撑以下三条路线：

1. **K／仅整理知识**：资料暂存、原文与既有知识核对、知识候选、受控正式维护，不生成学习约定或学习记录。
2. **L／仅学习**：学习约定、已审知识投影、DeepTutor 课程、学习记录与结果交接，不把学习完成当作正式知识接受。
3. **C／组合与沉淀**：知识与学习发生顺序或反馈关系，至少分别审查 C1「学习后回顾、纠错并形成修订候选」、C2「用户明确要求的先学后入库」和 C3「资料整理与学习并行」。C2 是本次任务的顺序约束，C1 是学习后的反馈关系，二者不得互相替代。

正式审查必须逐行填写以下路线验收矩阵；未执行或证据不足时如实标记，不用静态设计覆盖实际闭环：

| 路线 | 最少操作序列 | 闭环判据 | 失败出口 |
| --- | --- | --- | --- |
| K | 私有原件／已登记 raw → 查库与已审知识 → preview → 既有受管候选接收／独立审查 → 正式维护前的具体差异 | 无学习产物也能得到可交接候选；知识引用、内容范围和原始输入未在交接中丢失 | 缺角色或具体授权时保持待处理；preview 不自行批准 |
| L | 已审包＋有效约定 → 投影与课程步骤 → I4 → 显式 I5 → 另一 Agent 追溯依据 | 课程、学习记录、内容基线和准备依据可按各自边界解析；不推出权威掌握 | 缺输入、审阅或版本即停止；未知发送先对账，不换 ID 重发 |
| C1 | 显式学习回顾 → 错题／新事实定位 → 原文核验 → 知识或课件新版本／修订候选 | 原答案、旧基线和历史学习证据保留；新事实不会从聊天直接入库 | 未核清前限制相关学习观察的用途；修正分别回知识或课件流程 |
| C2 | 记录本次先学后入库约束 → 完成约定学习与回顾 → 形成候选 → 既有正式维护 | 顺序约束只约束本次任务，不形成所有知识维护的循环依赖 | 用户改变顺序或范围时形成新认可，不暗中复用旧约束 |
| C3 | 创建课程 → 正常入库／分类迁移 → 局部失效 → 重新核验续接 → 同活动继续 | 新旧准备版本及学习证据均可追溯；实质扩范围另取认可 | 无合法续接入口时明确阻断，不删除 guard 或沿用 stale 准备 |

审查不是评选模块数量，也不是继续强化所有门禁。核心问题是：职责是否清楚，最小闭环是否真实可用，哪些复杂度产生了实际价值，哪些缺口会阻碍日常使用或造成错误信任。

本轮只读审查并新增审查文档，不修改现有业务设计或实现，不启动真实服务、不调用业务模型 API、不生成课程、不处理正式 raw／wiki、不提交或推送。宿主主 Agent／SubAgent 的审查调用仍按 §7.1 记录用量，不能写成零模型调用。必要的运行验证只使用临时库和测试替身，并与真实业务证据分开记录。

- 重新选型或否定 DeepTutor，除非发现当前目标下的决定性反证。

- 对真实模型教学质量、真实宿主认证、真实资料全流程作未经验证的背书。
- 直接修复发现的问题；修复候选由用户另行选择。

## 3. 审查视角与关键问题

| 视角 | 决定性问题 | 主要证据 |
| --- | --- | --- |
| 用户任务与体验 | 用户能否理解下一步、减少重复确认、完成学习和整理？失败后是否知道如何恢复？ | 三条用户旅程、工作单、本地手册、课程入口、状态与错误语义 |
| 外部 Agent 可操作性 | 新 Agent 能否仅凭公开入口正确执行？哪些语义仍靠主 Agent 记忆或人工拼接？ | CLI／JSON 契约、identity／digest／previous、审阅附件、回执、host 边界 |
| 架构与数据所有权 | 各状态是否有唯一权威？两条路线是否真正解耦？跨模块绑定是否完整且可失效？ | 总体架构、K0–K4、I3–I5、Runtime／Executor、存储与回执 |
| 实现正确性与韧性 | 已交付能力在重复、并发、崩溃、依赖变化、恢复和恶意／错误输入下是否保持承诺？ | 代码、负向测试、故障矩阵、组合测试、必要的最小复现 |
| 安全、隐私与信任 | 私有准备、operator_supplied、独立审阅、正式授权是否被清楚区分？证据包会不会泄露或形成错误信任？ | 数据流、外发边界、凭据、附件保留、Executor／approve、文档声明 |
| Token、性能与上下文 | 原始输入、输出、调用次数、缓存计费和本地计算分别是多少？哪些环节可脚本化、复用或按需加载？ | 主 Agent cacheRead／未缓存输入／输出、业务 API 账本、本地模型耗时、重试与审查返工、单位成功任务用量 |
| 网络研究与本地模型 | 搜索发现、抓取、抽取、筛选、整理和最终核验是否由合适角色承担？本地处理能否减少主模型输入且不损伤证据？ | 当前搜索与抓取代码、Defuddle／宿主能力、网页快照、正文抽取、检索、来源卡、原文定位、外发边界 |
| 可维护性与演进 | 文档和代码是否易接手？上游补丁和版本升级能否隔离？是否存在重复协议或永久历史包袱？ | 模块边界、补丁清单、文档状态、兼容层、测试组织、上游版本固定 |
| 对抗与简化 | 哪些故障可绕过当前保证？哪些能力可删除、合并或后置而不损害目标？ | 反例、未接线入口、重复真值、过度设计候选、替代解释 |

## 4. 分工与独立性

主 Agent 负责冻结范围、汇总、证据复核、重复项合并和最终取舍。SubAgent 只读，不修改文件；每个角色使用独立最小上下文，并提交“结论、findings、证据、合理替代解释、建议、未验证项”。

| 角色 | 职责 | 重点边界 |
| --- | --- | --- |
| 用户旅程审查者 | 从首次使用、日常学习、整理、回顾和故障恢复审查用户负担与闭环 | 不以文档完整代替实际可用；区分当前用户和假想多用户；同时判断网络研究步骤是否增加用户负担 |
| Agent 开发体验审查者 | 模拟无历史上下文的新 Agent，检查入口、协议、上下文、错误与成本 | 不把所有人工语义判断误判为应自动化；检查长文档、长回执和重复交接是否可脚本化 |
| 架构与契约审查者 | 核对模块职责、数据真值、版本／失效、跨链交接和文档一致性 | 不重新展开已废弃方案；本地摘要不得成为第二份事实真值 |
| 实现与故障审查者 | 深读关键实现和测试，寻找正确性、恢复、安全及组合缺口 | 已知 R1–R4 只核状态；测试替身不外推真实环境；检查缓存、重试和本地管线的失效路径 |
| Token 与网络研究审查者 | 基于真实代码逐项裁决 Token 优化、爬虫、搜索、本地检索和本地模型候选的适用性 | 不按行业趋势直接推荐；区分原始 Token、调用、计费和本地算力；关键结论仍回原文 |
| 上游与简化审查者 | 对照成熟 GitHub 项目的实际机制，提出可复用、可删除和可后置项 | 一手来源、固定版本；不因 Star 或功能多推荐接入；优先核对现有 Defuddle／宿主能力再考虑新同类依赖 |

每个角色都要说明其 finding 对 Token、用户负担和证据质量的影响，但 Token 数值由 Token 专项角色和主 Agent 统一口径，避免重复汇总。主 Agent 在初步汇总后可追加一次对抗复核，专门检查高严重度 finding 是否证据不足、是否已有保护、是否只是用户已接受限制。SubAgent 意见不是投票；结论以可复核证据和当前目标为准。

审查自身必须有界，不能用并行放大总成本：

- 先完成核心闭环审查：K／L／C1–C3、数据与证据、授权、恢复和已知 R1–R4 状态。核心问题完成分诊前，Token／网络研究扩展审查只整理已有证据，不默认展开新上游调研或实验；用户明确要求全面并行时须同时冻结相应预算。
- 主 Agent 在派发前为每个角色冻结主要文件、外部来源和运行探针清单。默认每个 SubAgent 最多深读 8 个主要文件、查询 3 个外部一手来源、执行 2 个最小运行探针，并只有 1 轮补证；确需超出时在追加前说明对应核心问题、预期增量和实际成本，由主 Agent 记录，涉及新增外部发送或费用时另取用户授权。
- 每个角色完成既定问题后即停止，不为穷尽所有可能问题继续扩读。达到上限仍有缺口时标记 `evidence_insufficient`，列出最小补证方法，不用猜测填满报告。
- 主 Agent 汇总各角色实际读取量、调用、重试和可观察 Token；宿主计量不可见时记 `unknown`，以文件数、来源数、探针数和轮次作为本次审查的可审计代理指标，不冒充 Token 硬上限。
- 初步汇总后最多进行 1 轮对抗复核；复核只处理高严重度证据冲突和已有缓解，不开启新的扩展主题。

## 5. 上游对照方法

优先复用本地固定源码和已有研究：DeepTutor、OpenMAIC、Open Notebook、Kotaemon、Lattice、open-notebook-mcp。重点比较：

- 来源、知识、学习内容和学习事实的分离。
- 人与 Agent 共用业务操作，而非共享整段对话。
- 显式范围、按需检索、短回执和完整原始记录。
- 确定性评分与模型语义评价的边界。
- 持久状态、幂等、恢复和版本迁移。
- 通过现有 HTTP／CLI／SDK 复用，而不是引入完整重复产品。

前期行业调研另形成以下候选依据，正式审查时仍需与真实代码对照：

- 确定性脚本、按需披露、短输出和可复用产物：[Agent Skills 最佳实践](https://docs.anthropic.com/claude/docs/agents-and-tools/agent-skills/best-practices)。

- 大结果落盘、摘要和 SubAgent 上下文隔离：[Deep Agents 上下文工程](https://docs.langchain.com/oss/python/deepagents/context-engineering)、[Claude Code SubAgents](https://docs.anthropic.com/en/docs/claude-code/sub-agents)。
- 会话裁剪与 Compaction 成本：[OpenAI Agents Sessions](https://openai.github.io/openai-agents-python/sessions/)。
- 缓存前缀、命中和费用口径：[OpenAI Prompt Caching](https://platform.openai.com/docs/guides/prompt-caching)、[Anthropic Prompt Caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)。
- 搜索与抓取：[SearXNG](https://docs.searxng.org/user/about.html)、[Trafilatura](https://github.com/adbar/trafilatura)、[Crawl4AI](https://github.com/unclecode/crawl4ai)、[Scrapy](https://docs.scrapy.org/en/latest/intro/overview.html)。
- 本地整理与检索：[Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)、[FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding)。
- 条件性方案：[GPTCache](https://github.com/zilliztech/GPTCache)、[LLMLingua](https://github.com/microsoft/LLMLingua)、[OpenAI Batch API](https://platform.openai.com/docs/guides/batch)。

若引用“当前”上游能力或许可证，再查询对应官方仓库／文档并记录 URL、访问日期和版本；固定提交下的行为不得写成上游最新状态。参考项目只用于证明某种机制存在及其取舍，不证明搬入本项目后有效。

## 6. finding 与结论规则

每条 finding 必须包含：

1. 标题、严重度、生命周期状态与处置。状态使用新增／已知待修／已修复待验／`stale`／已关闭／观察项；处置使用待裁决／修正候选／需用户选择／已接受限制／仅观察，不能用“接受限制”代替生命周期状态。
2. 设计或实现原文、文件、行号和依据文件摘要；必要时附最小复现和实际结果。
3. 影响的具体用户路线、模块与信任承诺。
4. 至少一种合理替代解释或已有缓解，避免把设计选择误报为缺陷。
5. 最小修正方向、需要新增的组合验证，以及是否需要用户作价值取舍；不需要新增验证时说明理由。

“已接受限制”必须记录 `accepted_by`、用户明确授权出处和日期，并附对应原始决定；没有既有授权时只能标为“需用户选择”或“建议接受限制”，审查者不得自行关闭。只有完成受影响验证的修正，或具有上述授权的接受决定，才能把 finding 标为已关闭；`stale` 一律未关闭。

严重度：

- P0：可能造成不可逆数据损失、严重越权或核心事实被静默篡改。
- P1：核心路线无法闭环、关键契约不成立、错误信任，或维护缺口已使核心路线没有可持续维护路径并可能系统性地破坏上述承诺。
- P2：重要可用性、成本、可维护性或覆盖缺口，有局部绕行且不至于系统性破坏核心承诺，但应计划改善。
- P3：局部简化、文档或体验观察，不阻塞当前路线。

维护问题不得仅因工程量大升 P1；审查者须写明核心路线、关键契约或错误信任受到的实际影响，否则归 P2／P3。

最终结论分为：保持总体方向并局部修复、需要重构某个子系统、需要重新选型、证据不足暂不能判断。另给出“立即可做的小闭环”“后续再做”“不建议做”三类建议，避免所有问题同时扩张为下一阶段。

## 7. Token 与网络研究专项

### 7.1 先统一节省口径

审查必须分别记录，不把“省钱”都写成“省 Token”：

| 类型 | 例子 | 不能误写为 |
| --- | --- | --- |
| 减少原始输入／输出 | 脚本过滤、短回执、有界检索、历史裁剪 | 缓存命中就等于原始 Token 消失 |
| 减少模型调用 | 确定性管线、精确复用、合并固定步骤 | 多 Agent 并行一定节省 |
| 降低计费或延迟 | Prompt Cache、低价模型、Batch | 实际发送内容必然减少 |
| 转移为本地计算 | 本地摘要、Embedding、Reranker | 本地 Token 和硬件成本为零 |

主 Agent／宿主的 cacheRead 是首要观察指标之一，同时保留未缓存输入、输出、cacheWrite、调用次数和重试；业务 API 按实报／估算／缺失分列，本地模型记录耗时、资源和可信用量，无法观察记 `unknown`。评价单位优先使用“每个被接受的知识包、完成的有效学习目标和成功网络研究任务”，不只看总会话数字。

### 7.2 Token 优化候选清单

正式审查逐项核对当前实现、真实消费者和证据：

1. 用量归因：主 Agent、SubAgent、Skill、MCP、循环、摘要、Embedding、业务 API 和本地模型分别计量。
2. 确定性脚本：正文抽取、Schema、去重、Hash、Diff、日志过滤、索引、引用、精确判分和状态检查。
3. 固定管线：脚本前置检查，模型只处理语义项，保存中间产物和下一动作，失败从断点恢复。
4. 渐进式披露：常驻规则最小化，Skill／工具／参考文档按需读取，不默认发送全部 Schema。
5. 大结果落盘和短回执：只返回引用、摘要、总量、少量预览、状态和下一动作，按需回读。
6. 会话生命周期：不相关任务开新会话；限制历史；按任务边界压缩；原始记录与模型投影分离。
7. SubAgent 隔离：只用于高噪声且独立的任务，返回精简结论；核算其自身调用和并行放大。
8. 缓存友好布局：稳定规则、工具和参考资料在前，动态任务在后；用真实命中率判断，不盲目增加缓存内容。
9. 有界检索：先索引和元数据，再少量候选和必要原文；不默认把整个知识库或全部网页交给模型。
10. 产物复用：正文、知识包、课件、研究和审查结果按摘要与依赖精确复用。
11. 模型、推理和输出路由：简单任务小模型，复杂任务强模型；限制输出格式、长度和无效推理。
12. 条件性方案：语义缓存、LLMLingua、自动摘要、Batch 和多 Agent 编排只有在对照实验证明净收益时采用。

### 7.3 网络研究管线候选

必须区分搜索发现与网页抓取，爬虫库不能替代搜索。候选链路为：

```text
用户问题
→ 搜索 API／宿主搜索／可选 SearXNG
→ URL 规范化、去重和数量限制
→ 普通 HTTP 抓取，必要时浏览器回退
→ 正文抽取、元数据和原始快照保存
→ 本地检索／Reranker 筛选
→ 可选本地模型生成结构化资料卡
→ 脚本校验 Schema、摘录和定位
→ 主模型读取资料卡与关键原文
→ 核心结论和冲突回完整证据核验
```

候选工具的适用性由真实代码决定，不预先选定：

- 普通文章优先核对现有宿主提取和 Defuddle；Trafilatura 是轻量正文抽取候选，避免重复引入同类依赖。
- Crawl4AI 是 JS 页面、Markdown、缓存和浏览器抓取候选；自托管抓取不自动等于具备其云端搜索能力。
- Scrapy 只在明确存在批量、周期性站内任务时评估，不为临时阅读几篇文章引入。
- SearXNG 是搜索发现候选，不是爬虫；仍依赖上游搜索引擎，需评估质量、限流、查询外发和部署成本。
- BGE Embedding／Reranker 是本地筛选候选；先证明关键词、索引和结构化关系不足，再增加向量检索。
- Ollama 本地生成模型可整理分类、标签、候选去重、检索词、分段摘要和带来源定位的资料卡；不单独裁决证据支持、冲突、正式入库或授权。

每份资料卡至少保留 `sourceId`、规范 URL、原始快照、正文摘要、抽取器及版本、完整／截断状态、候选主张归属、连续原文摘录、定位、缺失信息和 `reviewRequired`。脚本只能验证摘录确实存在及结构合规，不能据此证明语义支持。本地摘要不是第二份事实真值。

网络访问需遵守目标站点条款、robots、速率与现有授权，不以绕过登录、验证码或反爬为默认能力；保存和发送网页内容时分别核对隐私与外发范围。

### 7.4 适用性裁决矩阵

Token 与网络研究审查者必须对每项候选给出一种裁决：

- **已有且应复用**：真实代码已覆盖，当前问题是入口、使用或计量不足。
- **适用，优先验证**：存在明确高消耗场景，且能复用现有边界，预期净收益高于实现成本。
- **条件适用**：只在特定页面、批量、硬件、质量或隐私条件下成立。
- **不适用／后置**：重复现有能力、缺少当前消费者、损伤证据或运维成本超过收益。
- **证据不足**：真实用量、质量或代码事实不足，只给最小补证方法，不强行选择。

每项裁决必须写清：真实代码入口、当前消耗或缺口、适用／不适用原因、节省类型、证据质量影响、隐私与安全影响、实现和运维成本、最小改法、回退方式，以及分开记录的 `A/B 方案` 与 `A/B 结果`。本轮未获授权或未实际执行时，结果写 `not_executed`，只能作离线或条件性裁决，不得宣称实测净收益；不能仅凭“行业常用”“本地免费”“模型更大”作结论。

推荐的对照顺序为：A＝当前 Agent 阅读路径；B＝确定性抓取、抽取、去重和短回执；C＝B＋本地检索／本地资料卡。只有 B 的质量与收益不足时才继续评估 C，避免把本地模型变成新的固定开销。A/B 方案须固定任务集、输入版本、质量判据、计量来源和返工口径；实际执行另按 §9 的授权与边界记录。

## 8. 综合评判方式

主 Agent 不按 SubAgent 数量投票，而按以下顺序综合：

1. **先守核心正确性**：数据、证据、授权和恢复存在 P0／P1 时，不用 Token 收益抵销。
2. **再判断最小闭环**：用户旅程与真实代码是否支持 K／L 及 C1–C3，逐行填写 §1 的路线验收矩阵，区分连接缺陷和长期能力未建。
3. **交叉核对同一问题**：用户、Agent、架构、实现和 Token 视角分别给证据；冲突结论回到代码、原始请求和实际场景裁决。
4. **比较净收益**：分别比较主模型 Token、业务 API、本地算力、用户操作、开发维护、质量损失和返工，标明实测／估算／`unknown`；未知项不得按零汇总，证据不足时不给总净收益结论。
5. **形成组合建议**：明确哪些现有能力保留、哪些只做连接修复、哪些脚本化、哪些管线化、哪些本地处理、哪些不做。
6. **保留用户选择**：涉及教学质量、隐私外发、本地硬件投入、新依赖和真实预算的取舍单列，不由审查者代替决定。

最终报告至少包含：总体架构结论、分级 findings、§1 路线验收矩阵的实际结果、Token 消耗画像、网络研究与本地模型适用性矩阵、视角间一致与分歧、推荐最小闭环、后续验证顺序和明确不建议事项。

## 9. 验证与交付

- 静态核对：关键文档与代码交叉引用、入口与状态一致性、已知 R1–R4 当前状态。
- Token 核对：优先使用已有账本和真实调用记录；离线只能做输入规模与路径估算，不虚构节省比例。
- 运行核对：仅对影响结论且静态证据不足的路径执行最小临时测试；优先复用现有测试，不重复整套历史套件。
- 网络管线核对：正式审查不默认安装爬虫、下载模型或启动本地服务；先依据真实代码和既有证据选择，再另请授权做代表性网页 A／B。
- 结构核对：检查新增本地 Markdown 链接。对已跟踪交付文档执行路径限定的 `git -c core.safecrlf=false diff --check -- <paths>`；对未跟踪新文档逐个执行 `git -c core.safecrlf=false diff --no-index --check /dev/null <file>`，只将实际 whitespace 警告视为失败，并区分 `--no-index` 因文件不同产生的退出 1。对照审查前后的变更清单，确认本轮只新增／修改获授权的审查文档，未改正式知识和既有实现；不把全仓既有脏文件算作本轮改动。
- 交付物：本方案、`docs/design/knowledge-base-redesign-review.md`，以及最终回复中的优先级结论。
- 无法验证的真实模型、真实服务、真实宿主权限、网页抽取质量和真实用户体验必须单列，不用测试数量填补。

本文件目前只整理审查方案与行业候选，尚未对当前项目作适用性裁决；等待用户确认后再启动 SubAgent 和正式审查。
