# 课程内容与阅读体验探索方案

> 状态：阅读体验探索 v0.4；run-01（证据未公开，无法由本仓库独立复核：docs/design/evidence/learning-course-experience-exploration/run-01/README.md）已记录首轮用户反馈。课程内容生产的后续路线由[能力目标驱动的课程内容重构方案](learning-course-authoring-redesign-plan.md)承接；本文保留阅读器与课程内容的边界及渲染证据。
>
> **这不是实施方案，也不是执行交接。** 本文不构成安装 Skill／依赖、修改课程、编写代码、调用模型或部署的授权。文中的组合、样章、技术探针和探索顺序均为待验证假设。
>
> 后续审查应核对证据、挑战假设和提出替代方案，而不是按本文直接执行。

## 1. 背景

当前 目标课程项目 课程已具备正文、题目、个人笔记、补充练习和深入学习等能力，但实际试学暴露出另一类问题：系统功能逐步可用，课程本身却仍然像压缩后的设计摘要。

用户反馈集中在四点：

1. 正文不够容易理解，表达和观感欠佳。
2. 每章信息量不足，缺少支撑独立设计的例证和细节。
3. 页面几乎全是文字，缺少承担解释作用的图形与交互。
4. 章末没有便于核查和继续阅读的参考资料。

因此需要探索的不只是「怎样把文章写长」，而是：

- 如何组织学习内容，使用户能独立完成设计；
- 如何让文字、图、代码、练习和来源共同承担教学任务；
- 如何复用成熟方法，而不是堆积 Skill 或视觉装饰；
- 如何区分阅读器升级与课程内容改版，保护现有学习证据。

## 2. 第一轮独立审查结论

第一轮审查已读取现有讲义、相关前后端源码、release-21 交接和主要官方资料。主 Agent 又核对了关键事实，8 项修订均采纳：

1. Fumadocs 的接入成本需要先看 Tailwind 兼容性，不作为默认组件底座。
2. 现有 Block 目录不能替代单个 Markdown 正文块内的小节目录。
3. Diátaxis 用于区分内容用途，但不把 5 章强制映射成纯 Tutorial。
4. 贯穿示例与最终迁移考核不能继续使用同一个已展示答案的任务。
5. 可交付练习必须明确产物承载、反馈角色、补学与复验。
6. 阅读器改进与大幅课文改写走两条路径。
7. 来源清单只维护一份创作依据，证据表和章末资料从它整理。
8. 探索缩到一个完整机制，分别观察排版与内容改动，不串联全部 Skill 和组件探针。

详细修订已并入下文，不再保留与这些结论冲突的旧假设。

## 3. 已核实事实与未决假设

### 3.1 当前课程事实

2026-11-15 对日常课程做过只读核对：

- Book 为 <对象标识>，包含 5 个主章节、自动概览及深入学习子页。
- 主章节核心正文均为单个 `text` 块，通过作者正文交付写入。
- 章内已有学习目标、讲解、代码或练习，但内容铺垫和视觉层次有限。
- Spine 的章节包含 `source_anchors`，当前正文块的 `source_anchors` 为空，前端没有统一的章末来源区。
- 当前 Markdown 渲染链存在 Mermaid 检测与 Rich Markdown 渲染路径。
- 第 5 章现有任务（未随本仓库发布：docs/learning/geo-flow-agent/lessons/05-build-lab.md）与方案中的「Markdown 检查与报告发布」贯穿示例相同，不能单独证明对新场景的迁移能力。

上述只是当时快照。任何未来探索或实施都应重新读取实际状态。

### 3.2 当前阅读器与依赖事实

- 当前发行使用 Tailwind CSS `3.4.17`，不是 Tailwind 4。
- 当前已有 `react-syntax-highlighter` 和 Mermaid，新增高亮或图形能力需要避免重复建设。
- `PageOutlineNav.tsx` 按可见 Block 生成目录，观察并跳转到 `block-{id}`；不会展开单个正文块内的 Markdown 二、三级标题。
- 当前渲染器、课程块和学习关联共享同一页面，目录与图形改动需要验证保存划选等现有行为。

### 3.3 当前保护事实

- 受管 `author-block` 当前只负责 `text` 正文插入和修改，不是完整的多类型课程生成器。
- 当前课程已开始学习；既有作者交付接口要求未接受首次基线且尚无学习进度。
- 原生整书重建会删除全部 Pages 并重置 Progress。
- 原正文、原题和扩展 quiz 的保护仍然有效。
- 阅读器样式和导航改进可以保持原内容及学习记录身份；大幅课文改写则属于另一证据边界。

### 3.4 现有可复用能力

- DeepTutor 已有 `figure`、`interactive`、`animation`、`code`、`timeline`、`flash_cards` 等块类型及渲染器。
- 受管扩展尚未完整开放这些类型，不能由上游组件存在推断当前作者交付已经支持。
- 项目已有 Obsidian Markdown、JSON Canvas 和 Vercel Web Design Guidelines Skill。
- 现有受管作者交付、扩展链、预算、恢复、I4／I5 和部署纪律是约束条件，不是本次需要重造的目标。

### 3.5 尚未验证的假设

以下内容不能写成事实：

- Mermaid 一定能在当前所有页面宽度、深色模式和长中文标签下正常显示。
- 增加字数或图数量一定提高理解效果。
- 用户更喜欢某个预先命名的视觉风格。
- 同一用户先后阅读两个版本可以形成严格的因果对照。
- 无上下文 Agent 的读者测试可以替代真实用户试学。
- 任何第三方 Skill 或组件库的热度能证明其适合本项目。

## 4. 探索目标与边界

### 4.1 学习目标

理想结果是用户完成课程后，能够不看原文独立设计自己的 Flow／Agent，包括：

- 领域对象与执行对象的边界；
- Capability 契约和 Registry；
- Flow 模板与产物接线；
- 薄 Agent 的建议范围；
- 执行、恢复、确认和验收证据；
- 可验证的故障反例；
- 对一个未展示答案的新场景完成迁移设计。

审查和试学应先判断这个目标是否能由课程内容达成，再讨论视觉风格。

### 4.2 体验目标

1. 每章回答一个明确问题，并提供完整理解路径。
2. 每章包含真实源码例证、迁移示例和有反馈标准的练习。
3. 图形只在能解释机制时使用。
4. 每章末尾有可点击、可核查、说明用途的参考资料。
5. 桌面、窄屏和深色模式下均有稳定阅读体验。
6. 重生成、删除等现有操作可发现、可键盘和触屏操作。

### 4.3 明确排除

- 不制作公众号营销文，不用情绪或套话代替技术内容。
- 不制作机构 PDF 报告，不引入 A4 分页、封面或页眉页脚。
- 不把每章独立 HTML 直接作为生产课程。
- 不为了丰富而堆动画、渐变、卡片和交互。
- 不机械追求字数，不虚构数字、案例、引文或来源。
- 不通过解除内容保护来完成视觉改版。
- 不建设复杂课程版本、差异合并或进度迁移系统。
- 本探索不改变 wiki／raw 维护流程。

## 5. 方法与 Skill 的收敛分工

安装量和星标是 2026-11-15 的查询快照，只用于辅助判断来源成熟度，不代表功能适配、教学质量或运行安全。

### 5.1 内容：先目标、证据、示例和练习标准

[Diátaxis](https://diataxis.fr/)把技术内容分为 Tutorial、How-to、Explanation 和 Reference。官方记录了 Vonage、Gatsby、Cloudflare 等项目实践。

本项目不把 5 章强制映射成纯 Tutorial，而采用：

**任务主线＋就近解释＋按需参考。**

- 任务主线引导用户完成设计物；
- 权限、原因和架构取舍等必要 Explanation 就近出现在学习主线；
- 精确字段、对象模型和来源作为 Reference；
- How-to 只在出现独立真实任务时采用；
- 保留现有 5 章，不拆成 4 套栏目或新增页面体系。

Diátaxis 对 [Tutorial 与 How-to](https://diataxis.fr/tutorials-how-to/)的区分仍用于检查内容是否混淆「学习」与「真实操作」，不是强制拆页规则。

### 5.2 示例与练习：考虑先备知识和迁移

[The Learning Scientists](https://www.learningscientists.org/blog/2026/6/18-1)区分 Worked Examples 与 Retrieval Practice。对当前课程的启发是：

- 新机制先通过完整示例建立理解；
- 再用变化的练习检查迁移，而非重复同一个答案；
- 回忆和作答用于发现薄弱点，不把阅读量当作掌握；
- 示例与练习的效果依赖先备知识和任务条件，不保证固定配方对所有用户有效。

「Markdown 检查与报告发布」保留为贯穿项目。最终另设一个未展示答案、结构相近的新任务，用于观察用户能否自行划分对象、权限、契约和恢复规则。无需为此新增学习平台功能。

### 5.3 写作辅助：按需而非每轮串联

- [Huashu Report](https://github.com/alchaincyf/huashu-report)：在需要场景、机制、替代解释或证据纪律时按需参考；不使用 PDF 流水线。
- [Humanizer-zh](https://github.com/op7418/Humanizer-zh)：只有出现表达问题时才用于保真润色，之后复核事实与限定条件。
- 不以「所有内容都必须经过所有写作 Skill」为流程目标。

### 5.4 视觉与 UX：先选一个，不叠加指挥

两个候选分别有不同价值：

- [Design Taste Frontend](https://github.com/Leonxlnx/taste-skill)：视觉方向、真实内容样稿和多宽度复查。
- [UI/UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill)：可搜索的布局、UX、图表和技术栈规则。

第一次探索只选择一个，根据实际缺口决定，不默认串联两者。若只调整排版、目录和图形显示，可以都不安装，直接在接近真实阅读器的样稿中验证。

[Vercel Web Design Guidelines](https://skills.sh/vercel-labs/agent-skills/web-design-guidelines)继续负责焦点、键盘、触屏、深色模式和长内容审查，但不把合规等同于好看或学会。

### 5.5 Obsidian 的定位

[Obsidian Markdown](https://github.com/obsidianmd/obsidian-skills)和 JSON Canvas 可用于内容原型、Callout、Mermaid 和关系草图。

`cssclasses`、双链、嵌入和 `.canvas` 不会被 DeepTutor 自动识别。它们是创作工具，不是网页实现。

### 5.6 备选而非默认增加

- [Anthropic Frontend Design](https://skills.sh/anthropics/skills/frontend-design)：主题驱动的视觉原则。
- [Anthropic Doc Co-Authoring](https://skills.sh/anthropics/skills/doc-coauthoring)：上下文收集、结构迭代和无上下文读者测试。
- [Impeccable](https://github.com/pbakaus/impeccable)：Read／Operate 模式打磨；附带启动器和可能的二进制下载，不应未审查就运行。

当前证据已经足够支持首次小样例，不再继续大范围搜索项目。

## 6. 工程方案比较与筛选

### 6.1 默认对照：现有组件局部改进

阅读器探索首先使用现有组件，原因是：

- 不改变课程内容和学习记录身份；
- 不需要升级 Tailwind；
- 可以复用已有 Markdown、Mermaid、代码高亮、目录和学习操作；
- 能直接判断具体缺口，而不是先引入一套新主题。

只有明确某个组件的收益后，才比较局部移植与引入依赖。

### 6.2 Fumadocs：有明确缺口后再定向评估

[Fumadocs](https://github.com/fuma-nama/fumadocs)面向 React／Next.js，提供文档布局、目录、Callout、卡片和代码组件。

但当前兼容性限制已经明确：

- [官方主题](https://www.fumadocs.dev/docs/ui/theme)只支持 Tailwind CSS 4，当前发行是 Tailwind 3.4.17。
- 主题会引入自己的颜色、动画、工具和默认样式，不能视为无冲突的局部替换。
- [动态代码组件](https://www.fumadocs.dev/docs/ui/components/dynamic-codeblock)可以不使用 MDX，但这不解除 Tailwind 或主题兼容问题。
- 动态代码组件使用 Shiki，当前已有 `react-syntax-highlighter`，需要证明不是重复能力。

因此，阅读改版不默认依赖 Fumadocs 或 Tailwind 升级。只有具体组件缺口成立时，才比较局部移植和引入依赖的实际成本。

### 6.3 其他成熟方案

| 方案 | 可借鉴内容 | 当前不作为主线的原因 |
| --- | --- | --- |
| [Docusaurus](https://docusaurus.io/docs) | MDX、版本、搜索、i18n、信息架构 | 更适合独立文档站，整体迁移会重复动态课程与学习状态 |
| [Quarto Books](https://quarto.org/docs/books/) | 章节、交叉引用、代码、图和出版 | 主要解决出版与导出，不替代当前学习交互 |
| [OATutor](https://github.com/CAHLR/OATutor) | BKT、自适应选题和学习研究 | 属于另一套掌握模型与 React／Firebase 架构，不是页面方案 |

Nextra、MkDocs Material、Starlight、Jupyter Book 尚未做同等深度核对。只有出现当前候选无法覆盖的具体缺口时，才继续定向比较。

## 7. 阅读器探索

### 7.1 与原课程内容解耦

字号、行距、菜单、目录和图形显示属于阅读器改进，探索时应保持：

- 原 Book、Page、Block 和内容身份；
- 原学习记录与题目关联；
- 原受管保护和扩展行为；
- 原课程内容不变。

这条路径与大幅改写课文分开验证，避免无法判断改进来自哪里。

### 7.2 小节目录：从 Markdown 标题派生

现有 Outline 只按 Block 建目录，无法覆盖单个大正文块。候选方向是从 Markdown 标题派生小节目录，同时保留原 Block 身份。

需要验证：

- 重复标题和中文标题的稳定锚点；
- 内容扩展、重生成或局部更新后的目录刷新；
- 标题锚点与 `block-{id}` 的职责分离；
- 跳转、当前位置观察和展开内容的定位；
- 与文本选择、保存划选、笔记和块操作的兼容性；
- 空标题、异常层级和超长标题的显示。

暂时不必为目录拆分课程数据。

### 7.3 视觉方向

「技术图纸＋编辑部读物」只作为候选，不是用户已经选择的风格：

- 正文近黑色，强调色用于链接、当前位置和状态；
- 避免大面积渐变、彩色正文和连续卡片；
- 中文字体、字号、行距和段距形成稳定层级；
- 正文保持舒适行宽，图和宽表使用受控扩展区域；
- 普通正文不套卡片，提示、练习、图和来源使用语义容器；
- 动画仅在能解释机制时使用，并尊重减少动态效果设置。

样稿应尽量接近真实阅读器，不先完成精美独立 HTML 再重新实现。

### 7.4 图形技术

现有 Markdown／Mermaid 是优先验证对象，因为已有渲染路径，而不是因为已经证明效果最好。

真实样例需要回答：

- 中文长标签如何换行；
- 窄屏采用缩放、滚动还是重排；
- 深色模式对比度是否足够；
- 是否有文字等价说明；
- 与选择文本、保存划选和块操作是否冲突。

只有明确学习价值时，才进一步探索原生 `figure`／`interactive`。第 5 章的 Flow 设计工作区是独立后续候选，不是首次探索的依赖。

### 7.5 操作与状态

- 用可见「更多操作」菜单替代仅悬停出现的图标；
- 菜单提供文字「重新生成」「删除」；
- 键盘和触屏均可使用；
- 原正文和原题仍不显示未开放操作；
- 未审 AI 内容使用明确但轻量的标记；
- 外部来源使用真实链接和安全的新标签行为；
- 错误说明包含修复或下一步。

## 8. 内容与练习探索

### 8.1 内容骨架

每章可按需包含：

1. 具体问题或设计困境；
2. 可观察、可验收的学习目标；
3. 整体图景及必要的图；
4. 核心机制与就近解释；
5. 目标课程项目 真实源码例证；
6. 「Markdown 检查与报告发布」贯穿示例；
7. 比较、反例与常见误区；
8. 可交付练习、评价标准和反馈方式；
9. 参考资料与进一步阅读。

不再预设每章固定字数或图数量。内容长度由学习目标、证据和用户卡点决定。

### 8.2 写作约束

- 先建证据表，再写正文。
- 技术论断、迁移推演和未决问题分别标记。
- 保留否定、范围、条件、归因和不确定性。
- 每个段落应增加信息、例证或推理，不重复包装同一结论。
- 比喻必须支持推导，否则替换或删除。
- 重要机制应有反例或替代解释。
- 润色不新增未经证实的事实。

### 8.3 章节学习产出

| 章节 | 预期学习产出 | 候选图形与例证 |
| --- | --- | --- |
| 第 1 章 | 解释 Flow、DataSet、Agent 的职责与权限边界 | 三层职责图、意图到证据流程图、Runner 调用链 |
| 第 2 章 | 判断改参数、扩能力或新增模板，并接出合法数据流 | Capability 契约图、生产者—消费者图、Flow JSON 对照 |
| 第 3 章 | 区分 Draft、Flow、FlowRun、DataSet，设计恢复规则 | 对象关系图、状态机、故障时序图和恢复反例 |
| 第 4 章 | 限定 Agent 输出，区分执行成功、目标达成和用户确认 | 权限边界图、证据关系图、AgentAdvice 示例 |
| 第 5 章 | 对一个未展示答案的新场景独立完成最小设计 | 新场景设计、Flow JSON、能力表和验收清单 |

这些图是候选，不是每章必须完成的数量指标。

### 8.4 练习反馈闭环

样章阶段先用现有笔记或本地文件承载设计物，配人工可读的评价标准，不新增提交平台。

需要明确区分：

- 用户自评：用户对检查表的判断；
- Agent 建议：可修改的辅助反馈，不是正式掌握认证；
- 正式审查：由明确审查者按标准作出的结论；
- 选择题结果、阅读完成和 Agent 表扬：均不能自动转成「已掌握」。

判断错误后，先定位应补学的机制，再用变化练习或未展示答案的新任务复验。反馈来源和复验结果分别记录。

## 9. 来源与证据探索

### 9.1 单一创作依据

指定一份固定来源清单作为创作依据，至少记录：

- 来源 ID；
- 文件或资料名称；
- 仓库路径和固定提交；
- 可点击链接；
- 来源类型与适用范围；
- 支持的关键论断。

证据表引用来源 ID，章末资料也从同一份清单整理，避免证据表、章末资料和 `source_anchors` 各自维护不同 URL 或版本。

### 9.2 章末展示

候选标题为「参考资料与进一步阅读」。每条说明显示它支持的具体观点或机制，并区分：

- 直接证据；
- 辅助阅读；
- 本课程迁移推演。

样章可先用 Markdown 章末资料，不必立即开发通用来源系统。只有展示价值成立后，才讨论结构化 `source_anchors` 到 URL 的映射和通用组件。

来源可核查与 AI 内容是否经过正式审查继续分别表达。任何未来验收都应实际打开链接，核对文件、路径和固定提交，而不是只检查 URL 格式。

## 10. 最小可否证探索

首次探索不再制作整章多轮精修，而是选择第 1 章中的一个完整机制，例如「为什么 Agent 只提供建议，不能直接执行」。

样例只包含：

- 一个完整示例；
- 一幅确有必要的图；
- 一项独立练习及评价标准；
- 可打开、可核查的来源；
- 就近解释，而非只给结论。

### 10.1 排版与内容分别比较

为帮助定位改进来源，分别观察：

1. 原内容＋调整排版；
2. 改进内容＋相同排版。

记录：

- 用户实际卡点；
- 错误类型；
- 需要哪些提示；
- 是否主动查找来源；
- 能否解释机制并完成练习。

同一用户先后阅读会产生学习残留，因此这只是诊断性比较，不是严格因果实验。必要时可用难度相近的不同机制补充观察，但不得把内容差异误认为纯排版效果。

### 10.2 样稿环境

- 优先在接近真实阅读器的样稿中检查；
- 不先制作精美独立 HTML 再二次实现；
- 无上下文 Agent 读者测试只用于发现表达遗漏；
- 真实用户试学仍是必要证据；
- 不用字数、图数量或满意度单独决定通过。

## 11. 探索顺序，不是实施阶段

### E0：选定机制与固定来源

可能产物：一个机制的学习目标、固定来源清单、现有内容与页面问题、练习评价标准。

停止条件：来源不足或学习目标无法观察时，不进入样稿。

### E1：两种最小样例

可能产物：原内容＋调整排版、改进内容＋相同排版，以及必要图形和来源。

停止条件：图形没有解释价值或排版改动影响现有操作时，先修正样例，不扩大范围。

### E2：真实渲染与用户试学

可能产物：实际渲染截图、目录／锚点检查、用户卡点、练习产物和反馈记录。

停止条件：无法判断用户是否理解时，不扩写整章或全书。

### E3：决定是否值得继续

只有真实样例显示明确价值，才讨论：

- 扩展到整章或其余章节；
- 是否需要一个视觉 Skill；
- 是否需要结构化来源；
- 是否需要原生交互；
- 是否存在值得移植或引入的具体组件。

若决定实施，另写实施方案，明确改动文件、数据边界、预算、测试、回滚和部署授权。本探索文档不承担该职责。

## 12. 探索评价维度

### 内容与学习

- 用户能否解释机制，而不是复述术语；
- 示例是否完整，练习是否检查迁移；
- 用户在哪一步需要提示，提示来自哪里；
- 来源是否支持对应论断；
- 是否区分自评、Agent 建议和正式审查；
- 是否有重复、虚构、夸大或不必要篇幅。

### 视觉与交互

- 图是否比纯文字更清楚地表达机制；
- 1440 px、768 px、390 px 和深色模式是否稳定；
- 长标题、长标签、代码、表格和 URL 是否溢出；
- 小节目录是否准确跳转且不破坏保存划选；
- 操作是否可发现、可键盘和触屏使用；
- 来源是否可理解、可打开、可核查。

### 工程与学习边界

- 阅读器改进是否保持原内容及学习记录身份；
- 是否与现有 Page／Block／Progress 兼容；
- 是否引入不必要依赖或重复能力；
- 是否保持 release-21 的保护与扩展行为；
- 是否把旧版学习证据误当成新版掌握证明；
- 是否有充分理由进入实施，而不是仅凭样稿好看。

## 13. 两条未来路径的边界

### 阅读器升级

若未来实施字号、行距、菜单、目录或图形显示改进，保持原课程内容和学习记录身份，按实际前端改动验证现有行为。

### 大幅课程内容改版

若未来大幅改写正文、教学顺序和练习，现阶段采用独立新 Book 最容易落实：

- 保留旧课程；
- 不继承旧作答为新版掌握证明；
- 记录新旧替代关系；
- 不建设复杂版本差异合并和进度迁移系统。

这是一条当前边界，不表示未来任何小修订都必须新建 Book。

## 14. 剩余开放问题

第一轮审查后仍需真实样例回答：

1. 第 1 章选择哪个机制最能暴露当前理解障碍？
2.  Markdown 标题派生目录的最小实现是否会影响文本选择和保存划选？
3. Mermaid 对选定机制是否足够，中文长标签和窄屏表现如何？
4. 第一次探索是否真的需要安装视觉 Skill，还是现有组件已经足够？
5. 哪个未展示答案的新任务适合最终迁移考核？
6. 练习评价标准能否使用户和外部 Agent 作出一致、可解释的反馈？
7. 单一来源清单能否覆盖所有关键论断而不增加维护负担？

这些问题不通过继续增加工具清单解决，应通过最小样例、实际渲染和用户试学回答。

## 15. 当前暂定方向

以下是探索假设，不是实施决策：

- 先做第 1 章中的一个完整机制，不直接改写整章或全书；
- 内容采用「任务主线＋就近解释＋按需参考」；
- 贯穿示例与最终迁移考核使用不同任务；
- 阅读器和课程内容分开验证；
- 默认以现有组件局部改进为对照；
- 不让阅读改版默认依赖 Fumadocs 或 Tailwind 升级；
- 写作 Skill 按需使用，视觉 Skill 最多先选一个；
- 样稿尽量接近真实阅读器；
- 来源只维护一份创作依据；
- 大幅课文改版若未来实施，采用独立新 Book，不继承旧掌握结论；
- 所有 Skill 仅属于 Agent 创作与研究流程，不自动成为 DeepTutor 运行依赖。
