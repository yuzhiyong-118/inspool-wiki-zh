# 四份 ChatGPT 审查产出的复核与取舍

> 本文为上游 Harness 审查记录。审查证据（探针结果、原始材料、证据索引）未随本仓库发布；引用上游源码时绑定[上游来源清单](../upstream-sources.md)的固定提交与文件路径。文中结论为源码与离线探针口径，不含上游测试套件、完整运行时、模型 API 与原生沙箱的验证。

日期：2026-11-16。状态：研究结论，不是实施批准或架构冻结。

## 结论

**四份材料有明确借鉴价值，尤其是学习事实与执行事实的区分、教学定义与学习尝试的区分、学习归档与请求压缩的区分。但它们没有证明“自建补强一定比采用 DSH 划算”，也没有证明必须先建立完整课程领域模型。**

用户的目标仍是采用 Lattice 整个学习产品，把已有课程思考融入其中。不是抽几项能力另造 UI，也不是为接入课程先写一个通用 Agent 平台。

本轮读完四份文件，按原文段落的上下文解释主张，核验影响选型的源码事实。下文以主题合并重复段落，保留出处章节，避免把同一个观点在四篇中出现四次当作四份独立证据。**“找出合理的核心思想”只使主张值得讨论，不会自动使它成为项目事实；源码、测试和实际学习结果仍分别需要证据。**

## 从原文提取出的核心思想

### 1. 学习产品的连续性比执行框架的名称重要

出处：D1 §2、§6、§8；D2 §2；D3 §3、§7～8。

最小解释：用户正在看的材料、正在写的草稿、遇到的困难以及 Tutor/Flash/Coach 的分工，都要在换运行时后继续成立。任务是改善真实学习过程。

成立条件：新运行时能访问这些领域信息，并把结果送回同一个工作台。**不要求这些逻辑必须继续放在旧循环内部。** Lattice 的 `tools.py`、`bridge/turns.py` 已提供可以追踪的边界，因此“产品结合很深”证明需要适配，不证明必须重新实现整个产品。

取舍：保留产品语义；不接受从“语义不能丢”直接跳到“必须保留原 harness”。

### 2. 稳定事实、观察、评价和自评要可区分

出处：D1 §2.7、§9.4、§10～11；D2 §5.3～5.4、§7.3～7.4；D3 §4.2、§6、§8。

最小解释：模型说“答对了”是一次评价；用户提交了什么才是观察；用户觉得自己理解到哪里是自评。它们可能相互矛盾，应当保留而非互相覆盖。

源码支持：`model.record()` 保存 `id/at/actor/type/refs/data`；`tools.record()` 限制 AI 可记类型；Card 的学习者字段有专门保护路径。Journal 也有 action/undo，不是所有条目都是掌握证据，更不是完全重放领域状态的事件库。

取舍：采纳来源区分；评价应关联作品的固定版本和量规。不要把“自评归学习者”解释为客观任务通过条件也由自评替代。系统可以记录“本次测试通过”或“按量规未通过”，同时保留用户不同自评。

### 3. 教学定义和这一次尝试不是同一件事

出处：D1 §9、§10.2、§11.6；D2 §2.3、§4～8；D3 §5、§9 P1。

最小解释：任务改版不能改写过去成绩；重做不能覆盖首次作答；关掉对话不应让课程进度消失。一份定义可以对应多次尝试，一次尝试可以跨对话。

源码支持：Lesson 保存 `objective/state/body`，Practice 存在 Coach Thread 头里，包含 `seed/goal/file/source_message/state`。这足以支撑轻量练习，但没有提供文档提出的完整版本化课程执行契约。

取舍：采纳语义区分。**不采纳“因此必须立即增加 Course/Module/Activity/Attempt/Assessment 六个独立实体”的跳跃。** 单人样课可以先有课程定义版本、尝试 ID、任务 ID、首次答案、求助记录和评价引用；章节可嵌套在同一文件中。Topic/Route 可作导航，不能被当成达标的唯一凭据。

定义与尝试语义独立，也不意味着存储必须立刻分库、分服务；Practice 与 Thread 当前绑定在其适用范围内是轻量实现，不是仅凭耦合就成立的缺陷。

### 4. 引导练习和独立迁移测量的是不同能力

出处：D1 §9；D2 §6～8；D3 §3、§5、§9。

最小解释：在提示下完成只能支持“获得帮助后能完成”，不能直接支持“面对变化能独立做出来”。需要保存首次提交及其之前可见的提示。

源码支持：`project-based` 已写里程碑与验收；`placement-check` 已写诊断；Coach 规则甚至已有稍变的收尾挑战。它们是提示词层的教学意图，不是已经测得教学效果，也没有强制隔离答案的保证。

取舍：采纳帮助条件和评价语境的区分。不必因此新建一个 Agent 或独立服务。独立性只对系统能观察到的帮助负责，不能声称证明学习者没在别处求助。

对我们的实际意义：run-04 已有首次五问、分离反馈和短变式。接入需要保留这些，而非从零设计一套诊断/评价术语。优先修复同案因果叙事，再验证学习者是否能解释并迁移。

### 5. 执行生命周期要诚实表达尚未结束与结果未知

出处：D1 §5.5～5.6、§10.1、§11.3～11.4；D3 §7.1、§9 P2。

最小解释：请求停止不等于动作停止；没收到结果不等于没做；重启后不能盲重放可能有副作用的动作。

实际证据：DSH 管线在取消后等待工具结束、跳过未启动调用；日志修复区分 `TOOL_OUTCOME_UNKNOWN` 与 `TOOL_NOT_STARTED`。本轮探针验证了这些算法。同时不配合取消的工具仍完成写入，超时也等待它结束；模拟领域批量保存失败重试仍重复写入。

取舍：采纳语义，不照搬文档全部状态名。`recovered` 应解释为日志/会话可继续，不应把一个已中断 Run 改写成成功。幂等键必须稳定于“同一逻辑操作”，每次新建 tool_execution_id 并不能自动去重。

D1 §10.1 拒绝统一承诺 `resume_run()`，D3 P2 却包含它并要求相同语义。这是真正的设计差异，不是排版问题。采用 D1 的能力显式声明原则。

### 6. 一个事实可以有多种视图，但不能有两个独立修改的主副本

出处：D1 §10.5、§11.1～11.2、§18；D3 §8。

最小解释：UI 对话、运行日志、学习轨迹具有不同读者和用途。需要明确谁产生命令、谁保存执行、谁展示结果，故障时能补齐而不重复。

需要修正：D1 要求 DSH 持久 Session 必须能从 Lattice Thread 重建，否则每个 Run 新建 Session，**这个条件过强且方向有误**。简化的用户可见 transcript 本来就不含模型工具历史、压缩事件和原始请求信息，不能据此重建全部执行状态。每 Run 重建会丢掉 DSH 连续会话的收益，又迫使外层重新管理上下文。

更小的可行解释：选择一个模型执行历史权威；若用 DSH，则由 DSH 保存模型实际历史，Lattice 保留领域数据，产品 Thread 保存用户提交与用户可见投影。稳定的消息/事件 ID 与投递确认负责去重和补齐，原始执行事件无需从简化 UI 文本反推。若要求更换运行时，定义显式的导出/导入边界，允许切换到新会话并交接，不能假装任意运行时状态可无损迁移。

### 7. 授权必须在真正执行副作用的位置生效

出处：D1 §4、§10.3、§11.4；D3 §6.3、§7.1、§9 P0。

最小解释：Agent 不应借换工具或路径绕过学习者字段保护；正在编辑的内容不应被后台工作静默覆盖。

需要修正：把一个类命名为 Tool Gateway 不会使它成为强边界。如果同一 Agent 还拥有能写 Vault、`.git` 或规则文件的原生 shell/fs 工具，仍可绕过它。此前 Lattice 探针已经复现 shell 自行提交绕过保护、skills 目录漏保。

取舍：按资源实际权限及调用路径评估。DSH 接入时必须审查完整 profile 的默认工具，而非只增加三个学习工具就认为只有三项能力。对有副作用的领域工具补事务/幂等；对 UI、外部服务分别核对，不宣称一个账本就实现全局事务。

### 8. 上下文选择、容量、压缩、缓存、长期学习记忆需要分别评价

出处：D1 §2.4、§3、§10.6、§11.5、§12；D4 全文。

最小解释：先判断什么信息有助于当前学习任务，再保证请求装得下；既要保留当前任务连续性，也要保留可追溯原文；降低计费不能以丢掉关键条件为代价。

源码支持：Lattice 动态路线放在历史之后、窗口按半窗口步进；DSH 有完整请求计量、按模型容量计算压缩阈值、工具结果配对、摘要后改变模型可见面而保留日志。摘要请求重用原消息前缀和工具 Schema 的构造也存在。

取舍：采纳职责区分，不立即拆成 D4 的七个独立子系统。长久的学习记忆与为下一请求准备的压缩摘要目的不同，但可以共享基础设施、明确来源和适用时间，避免两份摘要互相放大错误。

DSH 默认摘要指令面向 coding assistant，并要求英文工程摘要；它不会自动保留教学最重要的首次错误、提示暴露、尚未掌握的前提、下一步诊断。**采用 DSH 也仍需教学压缩策略。** 同样，学习 Context Snapshot 可以随用户答题/文件修改在下一 step 更新，不应被理解成整场 Run 永不变的快照。

## 必须修订或限制的事实判断

| 原文主张 | 复核结果 | 对决定的影响 |
|---|---|---|
| D4 用固定 12 条与 DSH 对比 | 12 是配置缺失的 fallback；Tutor=24、Coach=40、Flash=12；半窗口使实际条数可能更多 | 缺 token 预算的判断成立，数字必须按角色说明 |
| D3 文件权限“较完善”、AI 不可改用户字段 | 直接 API 有保护；既有 H1 已证实旁路 | 应保留为目标不变量，不能记作全面保证 |
| D3 “Retry、History Window”是失败恢复基础 | 重试、历史裁剪、运行恢复属于不同机制 | 删去让 History Window 为恢复背书的推理 |
| D1/D4 普遍缺 usage 时估算 | Lattice 已发送但无正文失败仍可能 usage=null，见既有 H5 | 不能把缺失用量当零费用 |
| D1 SDK 能力仍仅“待确认” | 本轮读协议、server dispatch 与 Python Session；没有直接 per-session cancel 方法；通知不含实时 assistant chunk | 接入前需扩展官方插件边界或采用另一个已验证通道；关闭整个进程不是等价方案 |
| D1 Python SDK 不需系统 Node | runtime wheel 文档确认封装可执行文件；本轮未安装 wheel | 运行时启动不是决定性障碍；插件开发与事件适配仍有成本 |
| D4 增量投影更快 | 增量维护存在；`TokenMeter.measure()` 明写 O(surface)，会重定价并克隆节点 | 不作性能收益结论；未做基准 |
| D4 DSH 计量“更可靠” | 机制更全面；默认文本仍为 chars/4，不能保证中文更准确 | 需真实模型误差校准，不能以字段更多推断准确率 |
| D4 摘要前缀复用 | 源码确认构造；可配置不同摘要模型/Provider，真实服务端缓存还受路由与编码影响 | 可以作为候选优化，不能当已证实节费 |
| D1/D3 每种运行状态/证据独立管理 | 语义需区分；物理分存不是逻辑必然 | 最小实现可以共用存储并有类型/ID，避免为每个名词造一套系统 |
| D1 §13 让 Tutor 调 learning_record 写 answered | 与 §10.4 “真实用户回答由应用记录”存在潜在冲突 | answered 应从可信 UI 提交直接写入；Agent 只能引用或形成 judged |
| D3 Assessment 同时是验收标准和结果 | 量规定义与某次评价生命周期不同 | 即使同文件保存，也要固定量规版本与评价证据，不能相互覆盖 |
| D1/D3/D4 “保留并补强更划算”及主观评分 | 没有等范围实现/维护成本对比；只列替换代价，低估自建执行层代价 | 保留为假设，分数不进入决策证据 |

## 对下一步的具体影响

1. **课程线**：用 run-04 同一个案例作为验收内容。先修复标题与阶段的因果联系，保留首次回答、独立短变式和来源证据。用 Lattice 已有 Lesson/Practice/Journal 呈现一条学习过程；只有无法表达的必要信息才加结构。这里是建议，不在本轮改课或学习库。
2. **运行时线**：DSH 的核心机制已值得认真考虑。下一关是小型隔离适配：一个 Tutor 会话，实时回复、读当前学习状态、展示题目、可信 UI 回答、单会话取消。先证明公开插件/通道可补齐 SDK 缺口，再讨论五角色迁移；不预先重建整个 Lattice harness。
3. **比较范围对等**：原生方案也必须计入取消、持久化、压缩、升级和测试的维护成本。DSH 方案计入 SDK 扩展、工具桥、数据投影与预览版升级成本。两边都必须解决领域写入事务、用户字段保护和教学内容质量。
4. **选型门槛**：是否保留现有学习体验、是否能可靠停止当前任务、故障后是否明确结果未知、是否避免重复写入、是否维护可解释。缓存命中率与漂亮架构图不能代替这些结果。

因此，本次材料改变的是问题表述和验证顺序，不是直接作出替换或不替换的决定。最值得留下的是“让教学连续、事实可追、失败可解释”的约束；具体框架由对等的最小接入证据决定。
