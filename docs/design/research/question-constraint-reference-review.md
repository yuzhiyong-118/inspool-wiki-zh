# 出题约束方案引用项目复核

> 本文为历史设计记录，随设计迁移整理发布。文中状态与验收计数对应原文写作时点的环境，不代表当前部署或验收完成。私人证据未随本仓库发布，引用处以「证据未公开，无法由本仓库独立复核」标注；本机路径已抽象为占位符，执行时替换为实际路径。

日期：2026-11-12。对象：[预审题约束方案](../learning-question-constraint-plan.md) §3 引用的三个项目。本文是本轮独立源码阅读结论；未安装技能、执行上游代码或测试、调用模型，未修改运行时或课程。上游 SKILL.md 在此仅是研究材料，不作为本会话的执行指令。

## 结论

三个项目有借鉴价值，但分别提供**教学问题的组织方法、需求澄清协议、生成代码的外部验证实验**，不能合并视为已经验证的自动出题系统。

原方案可以保留“学习目标、来源、误解与题目显式绑定”的方向，但不宜按当前 R1–R6 描述直接实施。尤其需要纠正：关键词命中不等于场景正确；同一规则允许产生多个不同误解选项；代码执行实验不等于教学效果实验；上游的 checkpointed 实现也不等于严格阶段放行。

## 2. rederive：值得借鉴的是问题地图和递进提示

主证据：[README](https://github.com/EricJujianZou/rederive/blob/7f43edc0ee0e098e98f77b01187027238aba77c8/README.md)、[SKILL.md](https://github.com/EricJujianZou/rederive/blob/7f43edc0ee0e098e98f77b01187027238aba77c8/skills/rederive/SKILL.md) §3–§5。

它先将代码库整理成 5–10 个设计问题，每个问题包含 Problem、Given、按顺序加入的 Constraints、Decision、Options 和 Evidence。每条约束注明会排除哪个朴素方案。教学时先给问题，让用户提出方案，再逐条加入使其方案暴露不足的约束；卡住时给候选，两次答错后可提供不画出缺失解法的草图；用户提出更好的替代方案也可被接受。

**适合吸收：**

- 先建立“学习目标 → 问题 → 典型误解 → 反例／约束 → 提示 → 来源”的准备材料，再产生具体题目。
- 从真实误解构造干扰项，能说明错误原因，不只写几个表面相似的句子。
- 将问题地图交给外部 Agent 准备，内部教学消费者按需要取用；提示和反馈有来源可追溯。
- 约束递进适合架构推导课；接受满足条件的替代设计，避免只认可作者原方案。

**不宜照搬：**

- 它没有要求选择题的每个错误选项必须违反不同规则。原方案 R3 是本项目新增假设，不是该项目已经验证的规律。
- 它不要求所有课程都只有一个生效约束；“每次增加一条约束”是一种教学顺序，不等于现实问题只能同时受一条规则影响。
- “连续两次答错后提供草图”不等于“最多两次额外追问后停止”。原方案 §3.1 将两者称为同一收敛结果，表述过强。
- 它的“即使被要求也不揭示答案”是强教学偏好，不能作为我们的通用硬约束。用户请求解释、先修不足或提示预算耗尽时，应允许补讲、跳过和保存。
- 地图与日志是 Agent 生成的教学材料与观察，不自动构成已经掌握的证据。

## 3. audit-and-rederive：适合准备阶段的目标澄清与内容审查

主证据：[SKILL.md](https://github.com/jxzhang97/audit-and-rederive/blob/414d78f1d0abb46738adf0706c98c9a55031d40c/audit-and-rederive/SKILL.md) Phase 2、Phase 4；[讲解规范](https://github.com/jxzhang97/audit-and-rederive/blob/414d78f1d0abb46738adf0706c98c9a55031d40c/audit-and-rederive/references/explanatory-rederivation-style.md) §3–§5；[交付约定](https://github.com/jxzhang97/audit-and-rederive/blob/414d78f1d0abb46738adf0706c98c9a55031d40c/audit-and-rederive/references/deliverable-contract.md)。

它审计数学／物理推导，区分用户想解决什么、数学是否成立、解释是否自足。先比对原始目标与后续材料，列出有证据定位、下游影响、具体选择的缺口问题，并暂停。原项目即使没有发现实质缺口，也要求确认拟采用的解释。

**适合吸收：**

- 将澄清放在外部 Agent 的课程准备阶段：目标、基础、范围或来源解释有实质冲突时，给用户具体选择，确认后再整理。
- 已确认的学习约定在其适用范围内复用；后续请求实质改变约定时再澄清，避免每次出题重复确认。
- 将教学叙述与审计材料分层：学生看到问题、推理、例子与反馈；来源映射、版本和校验记录放在支持层。
- 内容审查分别判断目标、答案和解释，不能用格式通过替代其中任何一项。

**需要修正原方案的推论：**

- 白榆失败首先是“已有明确目标却生成偏移”。尚无本轮证据证明它是“目标有关键歧义却未暂停”。原方案 §3.2 将两者称为完全同型，不能成立。
- 事前澄清解决的是需求歧义，事后拒绝解决的是产物不合格，二者不能互相替代。
- 不建议照搬“没有缺口也每次暂停”。课程方向确认门禁已有明确用途，不应扩散为每道题的人工批准步骤。
- 原项目只要求使用读者可见的章节／公式定位，并不提供凭关键词判断场景语义正确的算法。

本地仓库未发现许可声明；本轮只总结机制，不复制其技能或交付模板。

## 4. admit-only-what-rederives：重点是消费者掌握校验标准

主证据：[预注册](https://github.com/veriker/admit-only-what-rederives/blob/2641c748f9556cb955da26bdf64a0ce148539fd8/exp_z5/PREREGISTRATION_PIPE.md)、[run_pipe.py](https://github.com/veriker/admit-only-what-rederives/blob/2641c748f9556cb955da26bdf64a0ce148539fd8/exp_z5/run_pipe.py)、[grader_pack_pipeline.py](https://github.com/veriker/admit-only-what-rederives/blob/2641c748f9556cb955da26bdf64a0ce148539fd8/exp_z5/grader_pack_pipeline.py)、[fam_pipeline.py](https://github.com/veriker/admit-only-what-rederives/blob/2641c748f9556cb955da26bdf64a0ce148539fd8/exp_z5/fam_pipeline.py)。冻结数据：[PIPE](https://github.com/veriker/admit-only-what-rederives/blob/2641c748f9556cb955da26bdf64a0ce148539fd8/exp_z5/RESULTS_PIPE.json)、[KSWEEP](https://github.com/veriker/admit-only-what-rederives/blob/2641c748f9556cb955da26bdf64a0ce148539fd8/exp_z5/RESULTS_KSWEEP.json)。

它让模型生成数据处理代码，用消费者固定的独立 grader 与保留输入校验结果。PIPE 的四步为解析、去重、舍入、排序，对照一次生成、整条流水线返工、分阶段生成和校验。不是让学生答选择题，也不是检查自然语言题面是否忠实于来源。

本轮重新读取的冻结 JSON 确实记载：PIPE 无辅助 0/150，final-only 恢复 0，checkpointed 恢复 73/150；KSWEEP 的两组恢复率数组与原方案所列一致。**这只核对了作者发布的结果文件，未复现统计结果或真实模型实验。** README 也说明原始逐样本运行单元未提交；不能把聚合数字一致当成完整独立复现。

源码揭示了原方案没有充分体现的限制：

1. `run_pipe.py:202–220` 在单阶段预算耗尽后仍加入最后一个候选并继续；最终再做端到端校验。因此不等同于“每阶段通过才进入下一阶段”的生产硬门禁。
2. `fam_pipeline.py:378–386` 为各阶段构造参考输入时运行的是 golden 前序阶段，提供了正确前置输入；不能直接类比我们现实资料处理中错误输入会逐步传递的情形。
3. 分阶段与整条生成不只改变校验时机，也改变任务分解、提示、示例输入和组合方式。不能据此断言本项目仅增加门禁就会得到同样收益。
4. `N_STAGE=3`、`N_FINAL=12` 是重试次数上限，不是 token 等额；四阶段各有初次生成，最多 16 次生成，整条分支含初次生成最多 13 次。实际提前停止会更少。不能由尝试次数推算本项目节省多少 token。

**适合吸收：**校验标准由消费者固定，生成者不能靠自报成功放行；小单元检查后仍做整体验收；返工有上限并保留失败原因；比较方案时预先规定质量与成本指标。我们的生产路径应保持失败即阻断，不能照搬其实验中的耗尽后继续。

**不宜吸收：**引入它的整个运行依赖、执行模型生成代码来验证普通课件、用其 0.487 数字推断我们的出题或教学收益，以及把尚未启用的 L0–L3 写成已经实测同构的现有链路。

## 5. 对当前出题约束方案的最小修订建议

| 位置 | 问题 | 建议 |
| --- | --- | --- |
| §3 调研依据 | 将机制类比写成同型、同构或效果已获支持 | 区分原始机制、作者结果、本项目迁移假设；补充上述源码限制 |
| §4.1–4.2 单一咬合约束 | 将一种教学策略设为全部题目的限制 | 一个主要考查目标，可有多个适用规则；按题目需要选用递进约束 |
| R1/R2 | 标识与触发词出现不能证明冲突场景成立 | 只报告“必需标识／字面条件命中”；目标和场景是否正确仍需内容审查 |
| R3 | 强迫错误选项分别违反不同规则 | 检查错误解释有依据；允许同一规则对应多个不同误解，不强制不同约束数 |
| R4 | “理由不得违反约束”无法仅靠字符串和集合证明 | 拆成结构检查与语义审查；只有存在完整、可执行的领域规则时才增加机器判定 |
| 选项映射 | 模板 A/B/C/D 与生成后选项可能发生内容变化 | 绑定最终题目版本及选项内容，再审校错误原因；不能只靠相同字母复用旧映射 |
| §5 规格流转 | 保存规格不等于生成、审查和恢复均绑定同一版本 | 明确规格如何编入实际生成请求，如何绑定最终题与来源，以及编辑／恢复时何时失效 |
| §5 可关闭检查 | 已绑定课程可能借关闭检查绕过要求 | 允许无绑定旧路径，但已有绑定不得静默失效；改变策略需显式重审 |
| 不改上游的前提 | 为保持载荷完全不变而限制设计 | 固定版本用于可复现；可用小范围受管补丁扩展真实输入与校验，不必另建生成引擎 |

一个不需要运行模型即可看出的反例：题干写“BY-042 核验 F-017 与 F-071，不存在编号不一致”，仍可同时命中所有标识和“不一致”触发词，但并不满足编号冲突场景。因此 R1/R2 是必要字面检查，不能被称为充分场景判断。

建议的最小准备材料是：**目标、来源定位与版本、适用条件、典型误解与排除理由、参考题与解释、可选提示阶梯**。这由外部 Agent 准备并审查；内部消费者负责展示、收集作答、按已审标准判分或反馈及维护学习状态。无需新增第二套进度账本。

## 6. 验证顺序与范围

先修正文中的过强主张，再推进本项目验证。零模型阶段至少覆盖：原失败产物、满足标识但否定冲突的反例、等价措辞、选项重排、同一规则的不同误解、题目或来源改版后旧绑定失效。此阶段只能证明确定性检查的覆盖与边界。

若需要证明生成质量或 token 收益，再单独安排授权模型对照：固定来源和目标，比较现有参考模板与目标／约束增强输入，统计目标命中、来源忠实、答案唯一、拒绝／修复次数及总 token；按统一审查准则评价最终内容，失败调用也计入成本。本轮未进行这些实验，未宣称节省比例或教学效果。
