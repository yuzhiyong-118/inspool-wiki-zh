# 上游源码级机制结论提取

本文提取自上游源码静态核实记录中**只存在于研究笔记、未随仓库发布**的机制级结论。与[关键发现报告](report.md)的关系：那份报告给的是选型结论与处理链发现；本文给的是**支撑这些结论的源码事实与复用边界**，以及研究过程中对首轮结论的更正。

> 研究是**只读静态审查**：未安装、未执行、未调用模型。全部结论为源码口径，涉及运行行为、延迟与真实模型表现的部分只能给源码推断。结论对应各上游的固定提交（见[上游来源清单](../../upstream-sources.md)），不代表当前上游版本。

## 一、六个项目的形态事实

| 项目 | 形态事实 | 复用边界的硬约束 |
| --- | --- | --- |
| **Lattice** | Qt 桌面应用：PySide6 的网页视图承载 UI，Python 侧通过 WebChannel 暴露唯一 RPC 通道。模型循环是自己实现的 OpenAI 兼容工具调用循环，不是某个 agent SDK | **没有任何对外接口**——无 MCP、无 HTTP API、无对外 CLI。Vault 副作用极重：启动即对整个工作树 `git add -A` 并提交，此后每 10 秒自动提交、每 2 秒全树扫描，并改写 `.gitignore` |
| **Kotaemon** | 文档问答应用（Gradio + LlamaIndex + LangChain）。**代码中完全没有课程、大纲、学习对象概念**，是检索参考而非课程底座 | 硬依赖极重；引用与问答层硬依赖另一个包，**拿不到独立的检索管线**。默认重排模型需要额外密钥，缺失时静默不生效 |
| **DeepTutor** | Python 调度器是默认路径；TypeScript 是可选的**实验性调度器**，不是并行实现 | TS 只替换调度器，模型调用与工具执行仍在 Python 侧；只有一条特殊模式才把模型调用本身搬进 Node。**「有两个引擎」的说法容易误导** |
| **OpenMAIC** | 课件生成 + 课堂播放 + 现场导演三段式；课程可检查、编辑、复用、导出 | 课堂形态强、状态与资源多；对外接口不收 URL，外部 Agent 要传资料必须自己下载并上传字节 |
| **Open Notebook** | 「资料库 + 双入口问答」：Chat 是单次模型调用，Ask 是多阶段流水线；`search` 是独立直连工具，完整绕开 Ask | **不是一个课程或教学系统**——全仓没有课程、测验、掌握度、间隔重复等学习领域概念。检索在 API 层是文本与向量的严格二选一，不做混合 |
| **open-notebook-mcp** | stdio 优先的 MCP server（可选 HTTP 传输），本质是纯 HTTP 客户端 | 与后端存在多处 API 形状分歧，部分工具**在当前后端上根本不工作**；没有课程链 |

## 二、机制级结论：值得直接借用的做法

这些是研究中最有复用价值的部分——它们是**机制**，不是功能清单。

### 2.1 上下文预算的正确做法

- **工具清单延迟暴露**：只把工具名与一行式描述放进系统提示，需要时才读全文。这直接对应上下文预算的正确做法，值得采纳。
- **滑动窗口按半窗步进对齐**：取最近 N 条记录时，起点按 N/2 步进，使连续两轮的请求前缀完全一致，从而命中服务端 prompt cache。**缓存友好**的设计而非巧合。
- **检索结果按块打分是主要成本来源**：默认配置下，每次提问约 12 次模型调用——1 次答案生成 + 1 次引用抽取 + **N 次逐块相关性打分**（N 等于 top-k，默认 10）。查询扩展默认不走。**引入逐块重排前必须先算这笔账**，否则成本结构会被静默放大。
- **上下文「预算」在不同路径上未必真截断**：某项目只有一条路径真正截断，另一条只做选择与计数。**不能把一个端点的截断行为外推到全部路径**。

### 2.2 工具加载的权限与累积

- **延迟加载后仍会再校验权限，而且校验两次**：加载入口检查一次，执行分发时再检查一次。只在加载时校验是不够的——加载与执行之间的状态可能已变。
- **已加载的工具 schema 会累积且持久化**：会话越长常驻 schema 越大，**这是设计使然而非缺陷**，但意味着长会话的输入成本单调增长，需要纳入预算。
- **能力目录是声明式目录，不是插件加载器**：目录项在首次调用时一次性读取并做多种一致性校验（版本、标识与文件名一致、依赖闭包等）。这个「声明 + 启动期校验」的组合比运行时动态装载更容易保持依赖可推算。

### 2.3 引用与证据回锚

- **字符级回锚是真正可用的 provenance**：模型抽取逐字引文，再用差异匹配模糊回锚到字符区间，最终在 PDF 上高亮。**这是可以单独抄走的一层**——不需要整套检索栈，只需要「抽取 + 回锚 + 高亮」三步。
- **证据装配的元数据要少而可读**：只带文件名与页码，不带内部标识，既可读又不泄漏内部状态。
- **命中来源标记不等于内容遵守来源约束**：正文可能把来源的封闭白名单扩展成自己的判断。**来源锚点存在只证明来源进了上下文**，不证明整段主张都有来源支持。

### 2.4 学习状态与记录

- **两套记录要分清**：会话记录与学习状态是不同层，各有自己的目录、格式与生命周期。把学习状态当聊天记录读，会漏掉掌握度、复习计划与薄弱点。
- **学习状态需要真事务**：某实现用 SQLite 的立即写事务、版本号比较交换与多重幂等键。学习记录被重复写入或并发写入是真实风险，不是理论风险。
- **掌握度有两类判定**：一类来自模型推断，一类来自可观察表现。**两者语义不同，不能写进同一个权威字段**，也不能把阈值当作普适标准——阈值本身是产品决策。
- **学习记录用序号做乐观并发**：记录带序号与期望序号，读改写时校验，能发现并发覆盖。

## 三、复用边界的硬约束

这些结论决定「能不能直接用」，比功能清单重要。

### 3.1 版本与仓库形态带来的论证限制

- **一次性快照的仓库不能做基于历史的论证**：某上游的仓库历史深度为 1，全仓是单次快照带入的。**因此不能论证「某功能后来被删掉了」**。引用该上游的结论时，只能说当前固定提交是什么样。
- **文档残迹不能当作当前能力**：同一快照里带着测试报告与截图，截图显示存在某个连接面板，但该面板不在当前代码中。正确表述是「文档残迹显示上游曾有或另有该形态，**但本快照不可验证**」。
- **文档与实际不一致会骗过依赖检查**：某实现顶层引入了 GUI 依赖，而每个核心模块都间接依赖它，所以「核心零 GUI 依赖」的说法会被检查骗过——传递依赖仍在。
- **结论要区分「域名层可行」与「整体可行」**：同一项目上，前者可行而后者不现实。可行的切分线通常落在**领域逻辑与传输实现之间**，不在产品边界上。

### 3.2 依赖与部署成本

- **作为库直接复用会把整个栈拖进来**：包括应用框架、检索栈、向量库与编排库。避免主框架只能靠「不装依赖再手工装子集」，这种做法很脏且易碎。
- **真正的应用级管线在另一个包里**：拿不到核心包就拿不到检索管线、重排、表格补全与作用域过滤的完整装配。
- **存储位置常与直觉不符**：某项目的数据不在用户配置目录下，而在配置文件所在目录下的应用数据目录里。
- **最小启动面可以很��**：会话存储默认可零配置；缓存服务仅在集成模块显式配置时需要；向量库仅在相关模块启用时需要。**但前端构建仍需特定运行时版本**。
- **重依赖需分清主依赖与可选依赖**：某项目的主依赖里并没有出现文档处理与爬取库，它们是可选的。**「重」这个判断必须区分必选与可选**，否则会高估成本。

### 3.3 接口与适配器的版本偏斜

适配器落后于后端至少一轮 API 演进是常见状态，具体表现为：

- **字段关联名不一致**：适配器发单数字段、后端只读复数字段；
- **必填性反转**：适配器里可选的上下文参数，在后端是必填；
- **请求体格式与端点声明不符**：发 JSON 体到表单端点；
- **响应类型假设错误**：某端点返回事件流，适配器无条件按 JSON 解析，必然失败。

结论口径：**适配器不能被当作「与本体版本一致的完整接口」**。评估外部 Agent 接入方案时，必须逐参数核对契约与后端请求模型，并把「契约与实现不一致」当作**已知阻断**而非待验证项。

### 3.4 检索融合与去重的实现细节

- **「混合检索」可能只是朴素拼接**：某实现把全文检索结果与向量结果直接拼接，**既不是倒数排名融合也不是加权融合**。按「混合检索」这个名字估性能会高估。
- **去重条件可能恒真**：判重时把文档对象与标识字符串列表比较，而对象未定义相等语义，该条件永远成立。后果是同一块内容在结果里出现两次。**这类缺陷只能靠读条件本身发现**，跑通路径看不出来。
- **分词器影响中文效果**：某实现的全文检索使用英文分词器，中文场景必须更换。

### 3.5 上下文压缩的两条路径不可混谈

某项目存在两条上下文路径：一条默认启用压缩，另一条由独立开关控制且默认关闭。**必须分开陈述**，否则会把一条路径的行为说成全系统的行为。压缩保留什么、失败时会怎样，两条路径也不相同。

另有一处更正值得保留：研究首轮曾以某个非默认路径的证据描述全项目的默认行为。复核后结论是——默认路径**同样有**滚动摘要机制，只是实现位置不同。正确表述是「两套实现各有自己的机制，**不能互相引用对方的保证**」。

### 3.6 会话与记录的生命周期

- **追加式记录与可回填目录并存**：会话记录追加写入，长对话靠组织器写摘要检查点。追加式不等于完整——历史可能只覆盖摘要之前的部分。
- **没有对外接口的项目无法直接接入现有工作流**：某上游的工作流「外部成熟 Agent 负责搜集核验整理」在它身上接不进去，只能自己包一层。
- **领域模型不兼容会贯穿全链路**：文档种类与元数据约定不同，需要改的不只是文件格式，还有关系字段与索引。

## 四、研究过程中的更正与保留的失败

保留这一节是因为它记录了**哪些看起来可靠的说法实际上有洞**。

- **首轮结论被自己推翻**：某上游「没有历史压缩」的判断被复核推翻，默认路径确实有滚动摘要。**首轮用非默认路径的证据描述默认行为，是这类研究最常见也最容易漏的错误。**
- **计数口径差异被区分**：子执行者记录约 714 个路由处理函数，主执行者复核为 715，差 1 属计数口径差异。引用时应写「约 700+ 路由端点」而不是给出精确数字。
- **失效条件被零模型复现**：上述「判重条件恒真」的缺陷，是通过读条件语义发现的，不依赖运行。**能用静态阅读判定的问题，不应花钱跑一遍验证。**
- **一处证据被判定为不可用**：某研究轮引用了与实际后端不一致的适配器行为作为证据，复核时该行为在当前后端根本不成立，结论被撤回。
- **明确未覆盖的范围**：内容抽取在外部包里、其内部实现不在核实范围；运行行为、延迟数据与真实模型表现全部未覆盖。**读取测试文件只表示「覆盖意图」，不表示「已通过」。**
