# 开源学习应用源码研究与架构建议任务手册

> 本文为上游选型与原始研究记录。上游源码副本与研究过程记录未随本仓库发布；引用上游源码时绑定[上游来源清单](upstream-sources.md)的固定提交与文件路径，结论与分析随正文发布。文中状态与结论对应原文写作时点，不代表当前部署或验收完成。

日期：2026-11-09；状态更新：2026-11-10。源码研究和后续 [D1–D3 设计收敛](research/upstream-learning/design-convergence/design-summary.md)均已完成；当前推荐 DeepTutor Book，入口为 [总体架构方案](research/upstream-learning/architecture-proposal.md) 与 [设计状态](research/upstream-learning/acceptance-request.md)。下一步另写有限实施任务书。下文保留原研究要求，不据此重新启动全量调研或产品实现。

本手册取代此前“部署并跑完整流程”的任务要求。本轮根据真实源码处理方式提出架构建议，不以安装、真实模型调用或流程测试作为完成前提。旧实验目录中的产物保留，不要求补齐或重做。

## 1. 目标与选型自由度

深入研究六个已下载项目，回答：它们如何处理资料、生成和展示课程、组织教学交互、控制上下文、维护学习状态，以及供外部 Agent 调用；我们应采用哪些完整应用、接口、模块或设计，整体框架应该怎样调整。

用户明确允许推翻原整体方案。三方部署、课件目录生命周期、自建 Agent、现有 Runtime 均不是必须保留的条件；已有投入不作为保留理由。完整采用成熟产品、直接调用 MCP／API、使用 SDK、抽取代码与自建都可比较，不预设某个项目获胜，不为了借鉴更多项目而全部组合。

需要满足的用户目标：

- 资料先收集，明确要求后再整理；不是每个链接都自动生成课程。
- 外部成熟 Agent 能利用已有知识，负责较重的搜集、核验、整理和知识维护。
- 用户有自己的学习界面，可查看内容、追问和答题；学习状态可持续保存并供后续整理使用。
- 内部可使用强模型，需要借鉴的是 harness、上下文和应用工程，不假设内部模型思考能力弱。
- 优先单机、单用户；共享目录和产品自有数据库均可选择，关注开发复杂度、运行开销与维护负担。

目标可以由产品和外部工作流共同承担，不要求每个产品原生包办所有环节。正式知识库规则仍以 AGENTS 为准；需要调整时提出具体建议，本轮不直接改规则。

## 2. 接手上下文与权限

工作区：`<知识库根目录>`（本机路径，不随仓库发布）。

先读 [AGENTS.md](../../AGENTS.md)、本手册、[首轮源码对照](upstream-learning-architecture-review.md)、[固定版本清单](upstream-sources.md)。需求背景不清时再读[架构讨论交接](course-consumer-architecture-handoff.md)，不默认加载全部 S0／S1 历史。

源码位于 `references/upstream/`。记录实际 HEAD 与 manifest 是否一致；有差异就说明版本，不自动 pull、checkout 或回滚。首轮对照仅作线索，关键判断需要独立核实，允许指出其错误。

允许只读检索源码、配置和已有测试，以及编写研究文档；必要时使用自写的纯文本／AST 分析脚本。不要导入上游模块触发初始化，不安装依赖、不构建、不启动服务、不调用被研究应用的模型 API，不实现产品适配。不需要密钥、Docker 或特定部署环境才能完成任务。

输出只写入本手册规定的研究目录。保留现有修改、上游克隆及旧实验产物，不修改正式 raw／wiki、AGENTS、现有业务代码或阶段验收状态，不提交／推送。

## 3. 项目范围与阅读深度

| 项目 | 必须研究的重点 | 深度要求 |
| --- | --- | --- |
| DeepTutor | 教学 loop、上下文、工具加载、目标／答案／Assessment、学习存储、对外接口和模块依赖 | 追踪核心生产调用链，区分 Python 与 TypeScript 引擎及接线 |
| OpenMAIC | 资料到课程、Stage／Scene、课堂展示、测验、学习记录、API 与 SDK | 追踪生成和学习两条链，区分库能力与完整应用配置 |
| Open Notebook | 资料工作台、提取／转换、检索、上下文选择、Chat／Ask 和 HTTP 服务 | 查清资料处理与模型调用边界，不把普通问答等同于课程系统 |
| open-notebook-mcp | MCP 方向、工具注册、能力发现、HTTP 映射和兼容性 | 核对与本需求相关的工具输入、返回及后端契约 |
| Lattice | Qt／前端与模型循环、教学工具、文件／索引／Git、记忆和结果记录 | 查清轻量方案的复用边界，不预设去 Qt 或重写后端 |
| Kotaemon | 提取、混合检索、重排、证据组织、引用和 MCP 工具 | 聚焦检索机制及是否值得单独引入，不穷举全部 UI |

不要求逐行审计全仓。先定位入口和责任归属，只沿影响结论的调用链展开；README、接口声明和测试是辅助证据，不能代替实际生产接线。

## 4. T0：固定研究基线

记录六个项目的实际提交、许可证和研究入口。核对主仓库修改，保留现场。确定证据 ID 和输出位置；无需检查本机能否部署。

## 5. T1：还原实际处理链

对主候选追踪以下链路，说明输入、主要步骤、模型调用点、数据结构、写入位置和返回方式：

1. 资料进入 → 正文提取／分块／索引 → 生成或检索使用的上下文。
2. 用户学习入口 → Agent／能力选择 → 课件展示或讲解 → 工具执行 → 页面返回。
3. 提交答案 → 评分 → 目标／进度更新 → 持久化 → 后续读取。
4. 会话延长 → 预算计算 → 检索／摘要／裁剪 → 下一次模型请求。
5. 外部调用 → 路由／MCP 工具 → 业务方法 → 可读取的学习或知识结果。

没有对应链路时标明已检查范围和“未找到”，不为填表虚构功能。指出真正的数据真值、错误与恢复处理位置，不能只画理想流程图。对资料型项目按适用范围追踪，不要求它们拥有教学链。

## 6. T2：比较机制与复杂度

按机制归纳，再比较项目，避免六篇互不相连的功能介绍。

| 维度 | 需要回答的问题 |
| --- | --- |
| 分层与职责 | UI、模型循环、领域服务、工具和存储如何依赖？哪些可独立使用？ |
| 资料与课程 | 固定文档、动态生成还是混合？来源如何定位和保留？ |
| 教学与评估 | 答案、提示、不同尝试和掌握度如何表达？事实记录与模型判断是否分开？ |
| 状态与稳定性 | 事务、版本、幂等、重启恢复、超时和重试在哪里处理？有哪些源码可见的保证与缺口？ |
| harness 与上下文 | 提示、工具 schema、检索结果、历史和摘要怎样进入模型？加载后是否累积？ |
| token 与调用 | 哪些步骤不用模型？哪些额外调用摘要、规划、判分、研究或 embedding？开销能否关闭？ |
| 外部接口 | MCP Client、MCP Server、HTTP、CLI 或进程内 Bridge？实际暴露和返回什么？ |
| 工程管理 | 包边界、依赖、配置、扩展点、测试结构、升级与上游补丁维护成本如何？ |

稳定性可以基于源码评价，但不能写成已通过运行测试。阅读已有测试时标注“覆盖意图，本轮未执行”。不要默认单机就不需要并发控制，也不默认工程化就必须使用微服务或插件平台。

## 7. T3：明确可复用入口

对每项建议说明复用层级：完整应用、现成接口、SDK、代码模块或设计思想。给出入口／符号、必要依赖、与用户目标的差异，以及我们还需要承担的职责。

重点复核首轮发现：

- DeepTutor 的工具延迟加载、历史摘要和学习领域服务是否接入相应产品路径，不能混用不同引擎的保证。
- OpenMAIC 的课程／学习记录／资产分离、本地评分、renderer 覆盖范围及完整应用的持久化依赖。
- Open Notebook 的资料范围、提取库、Chat 与多阶段 Ask，是否会产生额外嵌套模型调用。
- MCP 适配器的能力搜索是否改变工具 schema 暴露；文本／文件输入及后端必填参数是否一致。
- Lattice 的 Qt 是否真妨碍所需形态，Vault／索引／Git 副作用影响哪些复用方式。
- Kotaemon 的检索、重排和引用能否由首选产品已有能力覆盖。

不能把 MCP 配置页当作对外 MCP Server，也不为了统一形式而给现成 HTTP 再包装一层。源码契约差异可以确认，没有运行不能编造实际错误码或已验证的兼容结果。

## 8. T4：给出整体架构建议

至少比较：完整采用 DeepTutor、完整采用 OpenMAIC、必要的现成 API／MCP 组合、SDK／模块复用。允许提出更好的路线，但必须指明依据与具体机制。

给出明确推荐及理由，不能只留下“各有优劣、以后再看”。允许依据源码作附条件推荐，运行未知不妨碍完成研究；指出哪些条件会改变推荐即可。

建议必须覆盖：

- 用户一条典型使用流程，以及各步骤由产品、内部能力或外部 Agent 中的谁负责。
- 模块与接口方向、知识及学习状态的真值、来源和学习结果如何交接。
- 哪些直接采用、哪些需要薄适配、哪些确实需要自建；不要隐藏适配工作的职责。
- 原方案哪些取消、保留或改写，为什么；已有投入不是保留理由。
- 依赖与维护成本，是否引入重复存储、两套 Agent、多余工作台或全局运行时。
- 少量影响最终采用的未知项：哪些继续读源码可解决，哪些未来才值得运行验证。

每增加一个组件或中间层，都指出不能被其他组件覆盖的具体职责。无需为兼容旧方案增加复杂度；本轮只提交设计建议，不删除或迁移旧系统。

## 9. 证据与结论边界

每条影响推荐的判断用证据 ID 关联：项目、完整提交、文件、符号／紧凑行号、实际观察及适用入口／配置。可链接本地源码，建议补固定提交 GitHub permalink，不复制大段源码。

结论分为“源码确认”“条件成立”“架构推断”“待确认”。分别说明实际接线、必要配置、推理依据或具体未知。“有声明”“有实现”“主应用已使用”是不同结论；未找到不等于全项目绝对不存在。

对于 token，只分析输入构成、静态调用路径、复用和裁剪机制及额外成本；不要求 usage、账单或实测节省比例。字符／schema 体积等静态估算要说明方法，不当作真实计费 token。没有运行不能编造延迟、恢复结果、截图或通过记录。

## 10. 输出文件

统一写入 `docs/design/research/upstream-learning/`，不用旧运行验证的 fixtures、metrics 或 cases 目录。

| 文件 | 内容 |
| --- | --- |
| `report.md` | 关键发现、机制对照、推荐与缺口，结论引用证据 ID |
| `source-evidence.json` | 绑定提交、文件、符号／行号、适用路径的证据索引 |
| `architecture-proposal.md` | 面向本项目的完整建议、职责与接口图、旧方案取舍、必要适配 |
| `acceptance-request.md` | 完成范围、产物路径、证据覆盖、未决项与提交验收说明 |

以上是待执行者创建的交付物，本手册不预填结论。避免多份文档重复正文；不能只交项目功能列表而没有面向我们的方案。

`source-evidence.json` 使用数组，每项至少包含：

```json
{
  "evidence_id": "DT-CTX-001",
  "project": "DeepTutor",
  "commit": "填写实际完整提交",
  "file": "填写仓库内路径",
  "symbol": "填写实际符号",
  "lines": [1, 2],
  "observation": "填写实际处理方式",
  "scope": "填写适用入口、配置或模块",
  "certainty": "source_confirmed",
  "limitations": "填写尚未确认的接线或运行边界"
}
```

`certainty` 使用 `source_confirmed`、`conditional`、`inference`、`unknown`。示例不是已取得的证据；常规源码引用无需逐文件计算哈希，固定提交与准确位置即可。

## 11. 上下文成本与执行方式

- 先 `rg` 定位，再读必要片段，不反复读取整篇 README、全目录和全部审查历史。
- 及时记下处理链和证据 ID；压缩后从交付文件继续。
- 优先本地源码，仅在关键缺口需要时查官方文档，区分文档版本与本地提交。
- 如分给多个只读 SubAgent，按教学／状态、课程／界面、资料／接口分工，由主执行者整合证据与取舍；不让各 Agent 重复扫全仓，非必要不增派。
- 缺少运行环境、密钥或实测数字不阻塞本轮；将具体运行未知留作后续事项。

## 12. 验收标准

执行者提交研究，本对话主 Agent 验收，重点检查：

1. 六个项目在规定范围内被比较，关键结论来自源码，不只是 README 复述。
2. 主候选的处理链、存储真值和外部接口有接线证据，没有把库能力外推到整个应用。
3. 上下文／token 分析覆盖节省方式、额外调用及适用边界，没有虚构实测结果。
4. MCP 方向、工具注册和 HTTP 契约核对准确，可复用入口明确。
5. 整体建议围绕用户目标，能推翻旧方案，有清晰推荐、备选与具体取舍。
6. 新增组件、状态副本和适配层有必要理由，不把多个项目无解释地拼在一起。
7. 未知项具体、有限、与决策相关，不反过来要求部署整套产品才算研究完成。

没有安装、API 实测、UI 操作或运行指标，不构成本轮验收缺陷。源码误读、接线证据缺失、推论不成立或把旧架构当硬约束，需要修订对应部分。

验收方式是定点读证据所指生产代码、核对调用关系和推理，不要求重放完整流程。研究通过只表示架构依据充分，不表示部署、教学效果或生产稳定性已通过。执行者不代替主 Agent 宣布最终验收通过。

## 13. 可直接转交的提示词

> 请执行 `<知识库根目录>/docs/design/upstream-learning-source-research-playbook.md`。这是源码研究与架构建议任务，不是部署或实现任务。先读 AGENTS、手册、首轮源码对照和上游 manifest，基于本地固定提交追踪六个项目的真实处理链。重点研究资料与课件、教学和学习状态、上下文／token、MCP／API、扩展与可维护性；区分 README、接口声明、实现和主应用接线。允许推翻我们的整体框架，优先比较完整应用、现成接口与 SDK，不为兼容旧设计增加复杂度。给出明确推荐、可复用入口与取舍，按手册交付四份研究文档，由原对话主 Agent 验收。不安装依赖、不启动服务、不调用产品模型 API、不跑完整流程、不改正式系统；运行未知不阻塞本任务，不编造实测结果。
