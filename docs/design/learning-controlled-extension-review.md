## 结论

**方向正确，但尚不足以直接作为执行任务书。** 应保留原课程与原作答，开放有身份、可恢复的学习补充；需要先补齐内容关联、生成与提交、审查等级以及真实用户操作路径。无需推翻 DeepTutor，也不需要再建通用 Agent 或事务平台。

推荐产品形态是：**已发布课程保留原文；学习时可即时解释和练习；值得保留的内容保存为附属扩展；要成为正式课程材料时再升级审查。** 不要求用户每次追问都完成一次课程发布流程。

## 实施前必须补齐的问题

### P1-A：独立扩展审查尚未接入实际 I4／I5 关联规则

**位置：方案 6.3、6.4、8.3。**

方案承诺原基线不变、新增内容单独审查，却未定义两者如何被现有读取器同时识别。当前 I4 比较整个内容身份；I5 的记录关联还要求本次整个内容窗口与首次基线一致。合法追加后，新生成的交接包里原题的关联也可能变为 unknown。旧交接包原字节不变，不能证明新导出仍可正确关联。

依据：`tools/learning_book/baseline.py:385`，`tools/learning_book/records.py:236`，`tools/learning_book/handoff.py:269`。上述最小验证复核了摘要变化后的当前行为。

**最小修订：** 明确“首次课程内容＋已提交扩展”的校验关系。保留完整原始观察，分别验证原受保护内容是否仍一致、哪些差异由扩展提交授权、哪些差异无法解释；新增题关联到自己的不可变内容和审查记录。不能通过直接忽略所有新增字段或放宽整书摘要比较解决。父页面新增链接、spine 合成章节、页数等结构差异也必须在允许变化清单内，不能只比较旧题文字。

新增验收：先作答旧题，再追加讲解和新题，再作答并导出；检查旧题、新题分别关联正确，未审扩展不会借用原审查，篡改旧正文仍能被发现。继续保留 cooperative／submissionContent=unknown 的原证明边界。

### P1-B：长时间生成与短时间发布应拆开

**位置：方案 6.2、6.3、7。**

“未稳定事务阻断普通 GET”与“生成时整本课程仍可学习”之间缺少实现安排。直接把上游深挖放进现有作者 journal，容易在模型生成期间阻断整书读取；直接开放上游写入又会让半成品进入正式课程。

依据：`author_delivery.storage_barrier()` 对该书未完成 journal 统一拒绝读取；`create_deep_dive_subpage()` 先写 spine、子页、父链接，再 await 编译。现有作者恢复只覆盖 Book／Pages，没有 spine 的 before／after。上游深挖更新 page_count，但没有同步 chapter_count，严格结构校验仍需补齐。

**最小修订：** 在课程目录内保留请求专属候选产物，生成期间不发布父链接或更改正式 spine；候选落盘、结构检查后，重新校验目标与 revision，才进入短提交。复用现有文件存储和 journal，但明确扩展其 spine、全新页面不存在态、父链接、映射、计数和响应恢复边界。候选不是第二套学习状态。

明确 requested／generating／generated／committed 及 failed／uncertain 的恢复结果。响应未知先对账；确认已发送但缺少完整生成结果时允许保持 uncertain，不能承诺任何崩溃点都能自动完成，更不能暗中重新调用模型。

协调锁不能跨模型 await 长期持有；同步线程 RLock 不等于异步任务锁。仍限定单本地服务进程，复用 runtime 的异步任务协调，验收多标签并发、生成期间阅读／作答、短提交中断和重启恢复。

### P1-C：现有补题链不能原样复用，必须列出两层接线差异

**位置：方案 4.3、6.4。**

项目层 `Production._produce_questions()` 拒绝已存在首次基线的新请求；服务端 `question_publication._target()` 也拒绝已学习或已接受基线的 Book。只增加扩展 API 或放开存储屏障，仍无法补题。

依据：`tools/learning_book/production.py:564`，`patches/deeptutor/e1-authored-delivery/source/deeptutor/book/question_publication.py:151`。

**最小修订：** 单列扩展生产操作，复用题目规格、来源／讲义绑定、选项顺序、请求对账和审查校验；新增题块与发布同一次受管提交，不先暴露空题。首次成课的原限制保留，由扩展操作校验新增目标、既有内容不可改、扩展来源和目标范围。不要通过清空学习进度、取消首次基线标记来复用旧入口。

完整页面规划器可能顺带产生普通 quiz 等块，必须显式限定允许的生成类型和后续处理，不能让它绕过受管题目链。

## 用户体验与复杂度建议

### P2-A：审查分级，避免每次学习补充都变成发布任务

**位置：方案 6.1、6.3、7。**

文档要求操作者、审阅证据、独立 I4，但没说明谁来审、何时能看和答。若每次“举例”“再练一道”都等待外部 Agent 完成全套审查，学习仍会被阻断。

建议区分以下行为，共用现有持久化能力，避免新建多套服务：

| 行为 | 用户体验 | 证据含义 |
| --- | --- | --- |
| 个人笔记／划选 | 即时保存，允许修改和隐藏 | 用户资料，不代表课程事实或教学审查 |
| 即时解释、例子、练习 | 在当前页边直接显示，记录请求与用量 | AI 生成、未经内容审查；练习反馈供参考 |
| 保存为学习扩展 | 用户明确保存，保留来源、生成身份和不可变内容 | 可再次打开、继续学习，仍不冒充已审课件 |
| 升级为正式课程材料 | 准备者／审查者按范围完成审查 | 才可声明正式内容审查和基线关系 |

这是对现有“所有扩展独立 I4”要求的设计调整，不能在未修订契约时当作已有豁免。即时学习结果也不得自动写入正式知识库或认定掌握。

知识范围变化时先用短句询问是否扩展；已有学习约定内的例子和练习默认继承约定，不反复让用户填写来源、摘要、revision 等工程字段。

### P2-B：幂等需要服务端保证，“同主题”也不能永久只允许一份内容

**位置：方案 4.2 第 6 点、6.3、8.2。**

上游前端会根据 `deep_dive_pages` 打开已有页面，但后端 `create_deep_dive_subpage()` 没有同主题查重分支，不能把前端行为描述为服务端幂等。原生 supplement 虽查 topic，但分三次插入；中途失败时也不等于整组补充已成功。

建议：相同 requestId＋相同摘要返回同一结果；相同 ID 改输入冲突。跨请求复用按父页／选区、操作、学习目标、难度和来源版本等有效条件定位，避免相同主题的“再给一道不同题”被永久复用旧题。界面提供“打开已有”和“再生成一份”，后者明确形成新请求并计费。刷新和超时保留原请求身份。

### P2-C：先恢复可发现的学习动作，不必先补全所有原生区块

**位置：方案 3.1、6.5、7。**

`DeepDiveBlock.tsx` 在没有 suggestions 时直接不渲染；已有正文课即使后端放开，仍不一定出现深挖入口。缺少闪卡、时间线等不是此次保护冲突的直接根因，也不必作为修复前置条件。

建议在正文选区／页边固定提供“解释一下”“举个例子”“再练一道”，复杂的“插入区块”放在次级操作中。先支持文本和受管 choice，不支持的类型清楚禁用。生成结果完成后提示用户查看，不自动跳离正在阅读的位置；推荐主题可后加，不必先多调用一次模型生成建议列表。

### P2-D：可选扩展不应增加主线学习负担，纠错不必复制整本课程

**位置：方案 5、6.3、9。**

应区分主线必学内容与可选扩展，给扩展提供隐藏／归档入口；保留历史字节、题目身份与作答。不因多开几个深挖页就要求重学主线或自动降低完成度。现有 Progress 主要按页访问与题目记录存储，文档尚未定义扩展如何参与用户进度展示。

原正文有误时，默认先提供勘误或有替代关系的局部修订，原文与原作答仍可追溯；只有学习目标和目录显著变化时才派生整门课程。不要把个人笔记修改也套用“派生课程”规则。本轮可以只支持勘误，课程级版本管理另列任务。

### P2-E：补齐单次动作的预算与回退读写边界

方案有累计预算门禁，但深挖完整页面可能调用多个生成器，原生 supplement 会生成提示、解释、题目三块。需要限定每次动作的最大页数／题数、上下文与输出上限、生成轮数；全部模型调用沿用同一本账本。超额停止生成，不停止用户阅读、笔记和现有作答。只发送当前相关页、选区和必要来源；不默认重发全书与全部历史。

前端显示预计工作量与完成状态即可，不要求每次弹出复杂预算审批。准确用量来自实际计量，不能把一次点击当作一次模型调用。

旧 release-06 没有扩展 journal 恢复逻辑，保留最新数据还不等于旧程序能安全读写。回退验收须证明兼容；不兼容时停用新写入并保留最新数据，明确只读或停止服务，不能让旧程序静默忽略新状态，也不能还原旧账本覆盖新增用量。

## 建议的最小实施顺序

1. 先补齐上述三项 P1 的接口与验收约定，并确定即时生成与正式审查的区别。
2. 验证“已存在旧作答→追加一段解释／一道新题→继续作答→新 I5 导出”的纵向闭环，包含普通写入拒绝、未知结果对账、短提交恢复和预算。它决定设计是否真正可用。
3. 接入可见的页边操作、未审标识、保存／打开／再生成、隐藏；保证失败不影响继续阅读。
4. 在同一条扩展链上增加深挖子页，补齐 spine／计数／父链接恢复和可选进度；不并行扩展所有块类型。
5. 独立验收后按原部署门禁接入日常，再由用户实际试学。真实模型验证另按材料和预算授权执行。

以上顺序不意味着重新设计整个学习系统。目标是补齐一次真实学习动作的完整闭环，让工程约束由系统承担，让用户能连续学习。

### 采纳判断

| 补充 | 判断 | 理由与边界 |
| --- | --- | --- |
| 每次扩展一份权威提交记录 | 采纳 | 一组新块／新题／结构变化要有一个提交结论；可复用旧序列化、校验和原子写方法，不能让两个旧 journal 各自提交后拼成成功 |
| 统一屏障、启动恢复及锁顺序 | 采纳 | 可避免一套恢复看不到另一套半提交；实施前还需给出唯一协调入口和实际锁顺序，不能只写“统一” |
| 候选／短提交／恢复／冲突读写矩阵 | 采纳 | 生成时可继续学习，短提交可短暂冲突，优先保证不混读和不丢输入 |
| 从首次基线验证全部合法增量 | 有条件采纳 | 应验证内容提交链，不能把所有 Book revision 都当成连续扩展序号，也不必在每次普通 GET 完整重放 |
| 补充练习及深入学习均为必交 | 采纳 | 用户明确需要原有功能，分阶段验收不能替代最终完整交付；无需扩大到全部块类型 |
| 正式审查升级、勘误等只留语义 | 采纳 | 本轮明确展示未审状态，不展示占位功能；延后工作不能削弱当前来源、结构与质量状态校验 |
| 新增检查要求旧实现先失败 | 需调整措辞 | 应证明有代表性的旧缺陷及新功能缺失，而非要求每个安全负例都变红 |

### 实施接口冻结前需要澄清的两项

**P1-D：Book revision 与扩展链序号必须分开。**

方案 6.6、8.1 把“按 Book revision 重放”和“revision 断档失败”并列，容易被实现为 `afterRevision = beforeRevision + 1` 且下一条必须无间隔连接。当前 `_claim_content_mutation()` 的职责是在执行操作前保存下一 revision，而非记录已成功提交的内容；其文档也明确 pause／resume 等生成命令属于领取 revision 的操作。它不是专门的扩展提交序号。正式内容、个人笔记、控制操作各自是否改变这个令牌，需要在新增接线中逐项定义，不能默认等价。

依据：`patches/deeptutor/e1-authored-delivery/source/deeptutor/api/routers/book.py:330`，其中 revision 在实际操作前于 `book.revision = current + 1` 保存。

建议在同一扩展记录内增加前一提交摘要和连续内容序号，绑定前后受保护内容摘要；Book revision 仅用于并发检查及记录实际前后值，不作为连续提交计数。非内容 revision 变化有明确分类，不以“数字跳号”单独判损坏；无法解释的受保护内容变化仍须拒绝。不需要新数据库或重做整个事件系统。

“乱序失败”也应指声明的链关系或操作顺序不合法，不指目录枚举顺序或 JSON 清单任意存储顺序。按明确顺序重建后验证前后关系，重复、缺失、分叉和未授权内容差异继续拒绝。

**P1-E：笔记与作答需要不同的保留办法。**

方案排除了 Progress 的恢复回写，但 user_note 本身是 Page.blocks 中的块，而扩展 journal 保存受影响 Page 的 before／after。仅写“进度不回滚”不能证明整页提交不会覆盖候选生成期间写入的笔记。

依据：`engine.insert_block()` 将 USER_NOTE 加到 `page.blocks`；`engine.update_block()` 也直接修改 Page；当前作者 journal 则保存整页图像用于恢复。learning-captures 是另一条独立保存路径，不能与 user_note 混为一类。

建议候选只表达新增内容，在短提交锁内重新读取最新 Page，再应用经过授权的增量并形成最终 before／after；若页面已不满足前置条件则保留候选、返回冲突，不从生成开始时的旧整页快照覆盖。恢复要区分扩展已提交后的合法笔记编辑与不确定的额外课程编辑，保证不回退较新 Page。也可先采取对该 Page 短暂串行／拒绝笔记写入的最小策略，不强行实现通用合并。

补充负例：生成期间新增或编辑 user_note，再提交扩展；提交期间产生笔记冲突；提交已成功后改笔记再启动恢复。三者都要保留笔记，未知冲突宁可停止对应内容写入，也不能恢复成旧笔记。作答仍按独立 Progress 和 submission_id 验证。

### 防止实施过重的两项约束

**P2-F：完整重放主要用于验收和 I4／I5，不等于每次读课都重放全历史。**

普通 GET 需要检查本 Book 是否存在未稳定提交，以及读取窗口是否稳定；完整增量核验用于正式核对、导出及恢复判定等需要证明内容的边界。可先实现有界的全链校验，达到容量门槛时明确返回容量限制，不必本轮建设事件数据库、快照平台或全局事务调度器。后续缓存只能是可丢弃且绑定链头的派生数据。

一份权威记录可以引用有摘要的独立内容附件，不要求把所有 Page 的前后全文和响应全部复制到一个巨型 JSON。长期导出须明确包体限制与诊断，避免每追加一块就复制整书、每次读课再搬运所有历史。完整证据也不应默认进入模型上下文。

**P2-G：旧实现失败证据要针对行为缺口。**

旧实现已经拒绝首次基线后的所有扩展，许多越权／空题／改旧内容负例原本就应通过，不应为了红绿流程改成失败。新增接口 404、缺少 import 或字段本身也不能证明旧混合提交缺陷。

建议区分：旧功能的真实失败复现、新行为的验收用例、始终应通过的保护性回归。对可在旧实现注入的中断／覆盖问题留行为证据；仅在新事务结构中成立的故障注入用例，在实现后验证，不要求为制造旧实现失败而做另一套临时实现。

### 复审结论

这些补充总体提高正确性，未改变已经确认的用户分工和原生交互。统一提交和完整内容关联属于这次功能恢复的必要工程工作；将其扩成通用事务／事件平台则没有必要。

建议采纳并先澄清 P1-D／P1-E，随后按原入口插入与新题闭环、整组补充、深入学习两步链推进。P2-F／P2-G 应同步写入执行约束。当前结论是设计建议可继续细化与准备验收，不能据此宣称实现或部署通过。

### 用户确认后的整理结果

- P1-D 已在设计中明确：Book revision 为并发令牌，内容提交序号、前一提交摘要和前后受保护内容摘要承担连续链验证；不以令牌跳号或物理存储顺序误判链损坏。
- P1-E 已在设计中明确：候选表达增量，短提交重读最新 Page，保护 user_note；作答和 learning-captures 分别回归；已提交历史不覆盖后来的笔记。
- P2-F 已在执行约束中明确：普通读取使用未决提交与稳定窗口检查，I4／I5 等证明边界执行有界全链核验；允许摘要附件，不要求巨型单文件，不新增通用事务平台。
- P2-G 已在验收与交接中改为三类验证：旧问题行为复现、新功能／新结构故障注入、保护性回归。不要求所有旧负例先失败。

以上是设计处理状态。接手 Agent 仍须先交实际接口／schema、锁顺序、容量及单次预算边界，再按完整必交范围实施和验证，不能把“意见已整理”写成“实现问题已关闭”。
